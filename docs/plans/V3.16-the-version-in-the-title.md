# V3.16 — The version in the title bar (F231)

*The owner: "I want a simple feature upgrade to test the new updater. What is a
simple one we can do". The new updater is V3.15's one-click update of an installed
Windows copy (F228), whose plan says the first real test is the next update. This
release is that update. Numbered F231, the next free ID, and shipped with it.
On the way the owner set F212 aside: "I want the app to be edmonton focused."*

## What a release that tests an updater has to be

- **Seen the moment the installer reopens the app**, with nothing to click.
- **Able to say whether the whole update arrived**, not only that something did.
- **Out of the code under test**, so a failed test cannot be blamed on it.
- **Worth having anyway.** There is no test channel: pushing a V-branch publishes
  the release, and every installed copy is offered it, the owner's friend's
  included.

The title bar is all four. Its words come from the program, which in an installed
copy lives inside `SiteAndPattern.exe` (PyInstaller's PYZ). Its number comes from
`version.txt`, a loose file in `_internal`. Help's *About / Version* label is the
same program reading the same file. So after Check for Updates takes an installed
V3.15 copy to V3.16:

| The title | Help menu | What it means |
|---|---|---|
| `Site & Pattern V3.16 — …` | *About / Version: V3.16* | The whole update arrived |
| `Site & Pattern — …` | *About / Version: V3.15* | Nothing changed: Windows' prompt was answered No, or the installer was cancelled or failed before writing |
| `Site & Pattern — …` | *About / Version: V3.16* | **Half arrived**: the old program beside the new `version.txt`. This is the state V3.15's `AllowSkipFiles off` exists to prevent, and the one that would tell the updater "up to date" from then on |

**Nothing on the update path changed.** The update from V3.15 runs V3.15's
`update_flow.py` (the offer, the download, the hand-over, the closing) and V3.16's
installer. `update_flow.py`, `installer.nsi`, `github_releases.py` and both
release workflows are untouched, so the installer that runs is the one V3.15
tested under Wine.

The other candidates, and why not: **F212** (below) depends on Nominatim being up
to show anything, so a failure would not say whether the update or the service
was at fault. **A "what's new" note on first launch** proves the same thing, but
it is a dialog at start, which the start screen, the welcome and every
window-constructing test would have to make room for.

## The change

- **`branding.window_title(document, *, version)`** builds the main window's
  title. `version` is a required keyword, so a new caller cannot leave it out by
  accident, and `window_title(version=None)` is still `APP_TITLE`: a copy that
  knows no release reads exactly as before.
- **`app_version.running_version()`** names the release. In an installed copy it
  reads `version.txt`. Windows' build writes that with `echo`, so with a CRLF,
  which `build_version` already strips. In a source checkout it reads the branch
  from `.git/HEAD`. It answers `None` unless the result is a `V<major>.<minor>`
  release. It is read once per run, because it names what is *running*: updating
  a source checkout switches its branch and then offers a restart, and until the
  restart the old code runs.
- **All five places that set the main window's title use them.** `app.py` sets
  it at start, on New and on Open; `persistence.py` on Save and when an autosave
  is recovered. The `*` for unsaved changes is appended as before.
- **Help → About / Version reads `running_version()` too.** It had worked the
  version out separately, with a `git rev-parse` process at every start. Now the
  label and the title cannot disagree, and a start runs one process fewer.

A source checkout on a release branch shows the number too. The owner's own copy
is updated by `git checkout`, and after the restart it reads `V3.16` as an
installed copy does. A development branch shows no number, and the Help menu
still says *dev*.

**Why `.git/HEAD` and not `git rev-parse`.** `update_flow` asks git, but only
when a person opens About or checks for updates. This runs at every start. A file
read needs no git on the PATH. Nor does it start a child process, which on
Windows opens a console window when the app was started without one. A detached
HEAD and a worktree (where `.git` is a file) name no branch, as `update_flow`'s
`_repo_path` treats them. A test checks the file read against `git rev-parse` on
the checkout the suite runs in.

## F212 set aside, on the owner's call

The owner: *"I want the app to be edmonton focused. So maybe dont waste effort on
that feature."* F212 asked for the address search to reach Saskatchewan. Its
backlog row also had the cause wrong. The correction is recorded here so that
nobody diagnoses it again:

- **The search has covered Alberta and Saskatchewan since V2.14**
  (`property_data.geocode_address`: `_PRAIRIE_VIEWBOX`, then a province filter).
  Only its words, *Search Alberta address* and *No Alberta results*, still say
  Alberta.
- **What limits it is the view bias.** Once the map has reported its centre, the
  Nominatim query is a box about 50 km either side of it, with `bounded=1`,
  which makes the box a filter rather than a preference. The map opens on
  downtown Edmonton (`html/map/01-core.js`) and reports its centre on load
  (`_emitMapMoved`), so a search reaches about 50 km from wherever the map is
  looking. From Edmonton that is the metropolitan region (St. Albert, Sherwood
  Park, Spruce Grove, Leduc, Fort Saskatchewan), which is what an
  Edmonton-focused app wants.
- **Not checked live.** This container's network refuses Nominatim (the proxy
  answers 403), so the `bounded` behaviour is Nominatim's documented one. It was
  not observed.

## Left alone, on purpose

- **The About box's wording.** On an installed copy it reads `Branch: V3.16` and
  `Commit: ?`: git's words, and a `?` that looks broken. It lives in
  `update_flow.py`, which this release keeps out of its diff.
- **The update offer's "What's new".** It prints the first 700 characters of the
  GitHub Release's text, which is the install instructions, with their Markdown
  asterisks showing. The text comes from the two release workflows, which this
  release depends on, so the fix comes after the test, not inside it.
- **The other windows' titles** (3D Preview, Growth Snapshots and the rest). They
  say what they are, and one version on the main window is enough.

## How it is checked

- **`tests/test_app_version.py`** (new, 15 tests, Qt-free):
  - The title with and without a version, and the required keyword.
  - `.git/HEAD` read on a branch, on a detached HEAD, with no checkout, with a
    worktree, and against `git rev-parse` on this checkout.
  - `running_version` in an installed copy, through a real
    `_MEIPASS/version.txt` with a CRLF, and never asking git there.
  - A build from no release, a source checkout on a release branch, a development
    branch, and read once.
- **`tests/test_philosophy.py`**: the rebrand guard now requires the title to go
  through `window_title`. It fails on a title built by hand in `app.py` or
  `persistence.py`, in one sentence. That was checked by putting one back. The
  first version printed the whole 900-line file as its message.
- **`tests/test_app_smoke.py`**:
  - The window's title at start.
  - New, with the version patched, reads `Site & Pattern V9.99 — Test yard`.
    It is patched so it holds on CI's pull-request checkout, which is detached
    and names no release.
  - The Help menu and the title name the same version.
- **Live**, in the real window, offscreen, driven through every path that titles
  it. The steps were start, New, an edit, Save, Open, and an autosave recovered:
  - **As a source checkout on the V3.16 branch**: `Site & Pattern V3.16 —
    Native Habitat Designer`, then `… V3.16 — Probe yard`, with ` *` after the
    edit and after the recovery. Help reads *About / Version: V3.16*.
  - **As an installed copy**: `sys.frozen`, with `_MEIPASS` pointing at a
    bundle holding `version.txt` = `V9.99` plus a CRLF, as Windows' `echo`
    writes it. Every step reads `V9.99`, and so does Help.
  - **The half-arrived row of the table, shown rather than argued**: the same
    installed-copy run against the unchanged V3.15 code (a temporary worktree
    of `305e55e`). The title reads `Site & Pattern — Native Habitat Designer`
    with no number, and Help reads *About / Version: V9.99*.

**The suite**, in this container, as CI runs it
(`scripts/run_tests.py --exclude tests.test_undo_redo --max-skips 25`, with
PyQt6, WebEngine, rasterio and pyproj installed).

- **The first full run** had 4,746 tests, one failure and 55 skips.
  - The failure was in this release's own test. The git cross-check called
    `subprocess` with `text=True` and no encoding, which
    `test_architecture_guard` refuses because Windows would decode git's output
    with the locale codec. Fixed, and the guard and the new module re-run green.
  - 44 of the skips were shapely and numpy missing from the container. The
    runner rightly fails a run with more than 25 skips.
- **The re-run**, with shapely, numpy and NSIS installed, was 2,000 tests in
  with no failure when this was pushed.

CI runs the whole suite on the pushed commit, and that is the record. This plan
was not amended afterwards, because a second push to a V-branch rebuilds its
release.

## What could not be verified here

- **Windows.** Two things there could not be checked here: the update itself,
  and the title as Windows draws it. The offscreen platform draws no title bar.
  `windowTitle()` is the text Qt hands to Windows.
- **The update itself is the owner's test**:
  - It needs a Windows machine with an *installed* V3.15. The owner's source
    checkout updates by `git checkout` and never runs the installer.
  - V3.15's installer stays on its release page after V3.16 is published.
  - Check for Updates should wait until both release workflows have finished. The
    updater offers the newest release whether or not its Windows installer is
    attached yet. Too early, it says *no installer for your system attached yet*
    and opens the download page, which is not the updater failing.
