# V3.01 — Filters people can read

*One item: **F194**, step 4 of the V2.98 review of perusing, selecting and placing
plants and communities. The review's finding 6 reads "Filters lose their labels,
keep stale ones, and hide their logic". V3.00 shipped part of the step with F192:
one filter set, a Clear button, and a folded line that says which filters are on.
The owner asked for the next step after V3.00: "Continue".*

## What was wrong

Measured on V3.00 (441ebcf) with the catalogue as shipped (424 species).

**A chosen filter loses its name.** A dropdown's only label is its grey
placeholder ("Any type"). Once a value is ticked the box reads "Shrub", and the
word "Type" is gone. Two ticked roles read "Larval Host, Bird Food", which says
nothing about how they combine. In fact they combine the opposite way from two
ticked types: Role keeps only plants with *every* role ticked, and every other
filter keeps plants with *any* value ticked. Only a hover tooltip says so.

**The stale "● Shrub" has a cause, found here.** V2.98 saw the Type box read
"● Shrub" with nothing ticked, above 16 asters. V3.00 could not reproduce it with
a mouse. Three ordinary inputs do it:

| Input | Then | The box reads |
|---|---|---|
| the mouse wheel over the closed Type box, two notches (scrolling the panel past it) | untick Shrub | "● Shrub", nothing ticked |
| ↓ with the box focused | untick Shrub | "● Shrub", nothing ticked |
| Space to tick Shrub in the open list, Return to close it (a keyboard walk) | untick Shrub | "● Shrub", nothing ticked |

Each one makes Shrub the combo's *current item*. A `QComboBox` draws its current
item's icon beside the text, and the dot is Shrub's colour swatch. And whenever the
current item's data changes, Qt rewrites the line edit with that item's name.
Ticking or unticking a box changes the data. Our handler runs first, because the
model's own `itemChanged` relay is connected before the combo's handler, so Qt
writes last. The scroll wheel alone leaves a coloured dot beside "Any type".
V2.98's walk was keyboard-driven; V3.00's check was mouse-only.

**An empty result says nothing.** "No plants match", under a list with nothing in
it. It does not say which filter emptied the list or what removing it would bring
back.

**The soil pH is a filter nobody chose, and nothing shows it.** Since V1.67, a
dropped pin fetches the soil and `set_soil_ph` narrows Browse to plants whose
recorded pH range reaches the site's, give or take 0.5. Nothing on screen says so.
What it hides, by site pH:

| Site pH | Shown | Hidden |
|---|---|---|
| 6.5 | 420 | 4 |
| 7.0 | 415 | 9 |
| 7.5 | 404 | 20 |
| 7.8 / 8.0 | 319 | **105** |
| 8.3 / 8.5 | 154 | **270** |

7.8 to 8.0 is ordinary for calcareous prairie soils. At pH 8.0 the hidden 105
include Bearberry, Bunchberry, Balsam Fir, Black Spruce and Blue-eyed Grass. Two
things make this worse than a plain filter:

- **Both sides of the comparison are coarse.** The site's pH is estimated for the
  area (the soil pack, SoilGrids or a regional default), not measured in the yard.
  The plants' ranges are reference values: all 424 rows have one, 35 distinct pairs
  between them, 102 rows read exactly 5.5–7.5 and 74 read 6.0–8.0. And unlike
  flower colour and nativity, nothing records where the pH ranges came from.
- **Only Browse applies it.** The Directory and the community builder have no site,
  so at a pin with alkaline soil the same plant is in one list and missing from the
  other with nothing to say why.

## The change

### A filter keeps its name, and says how it combines

Once something is ticked, the box reads its dimension first and joins the values
by the facet's own rule: "Type: Tree or Shrub", "Role: Larval Host and Bird Food",
"Blooms in: June, July or 1 more", "Restoring toward Aspen Parkland". Before
V3.01, three or more ticked values read "3 selected". Now the box names the first
two and counts the rest, so it still says how they combine. Values are named in the
facet's own order, whatever order they were ticked or set in: a chip that named
them in another order looked like another filter (it did, in the first smoke run).
The words come from one function in the vocabulary (`plant_filters.face`), which
the chips also use, so a box and its chip cannot disagree. The line edit is
scrolled to its start, because a `QLineEdit` given text puts its cursor at the end
and would show the tail. Live, a 202 px box clipped two roles to "Role: Pollinator
Support and Bird F", which still says what the box is; the chip above it says it
whole. A screen reader gets the face as the combo's name, where V3.00 gave it the
bare value.

**Each list opens on a line saying how it works**: "Tick as many as you like. A
plant needs one." For Role it says "A plant needs every one." The row is not
checkable and not selectable, and a screen reader meets it first. This answers
"the dropdowns look single-choice and are not". The checkboxes only showed that
once the list was open.

### The stale label cannot happen

`CheckableComboBox` now keeps no current item, ever. Any path that makes one
(the wheel, an arrow key, Return in the list, a call from code) is undone
straight away. With no current item, Qt has nothing to rewrite the text with and
no icon to draw. Two inputs also change meaning, because a multi-select has no
"next value" to step to:

- **The wheel scrolls the panel.** Before, scrolling the side panel and passing
  over a filter changed that filter's current item instead of scrolling.
- **↑, ↓ and Space open the list.** F4 and Alt+↓ already did, as Qt's own keys.

This is in the shared widget, so it covers the community library's facets too.
`tests/test_filter_widgets.py` drives each of the three inputs, then unticks Shrub;
all six of its stale-label and input tests fail on V3.00's widget.

### What is on, as chips you can remove

The folded line used to be one string, "Type: Shrub · Native". Now it is a row of
chips, one per filter that is on (`src/filter_status.py:FilterLine`). Clicking a
chip removes that filter. The example design, opened cold at 1366 × 768:

    Filters ▸  [Restoring toward Aspen Parkland ×]  [Your soil: pH 6.5 ×]
    Clear all
    339 of 424 plants                       Order [Recorded near this site]

Both chips are filters the app set, the pin's region and its soil, and V3.00 showed
only the first. Each chip's accessible name is "Remove Restoring toward Aspen
Parkland". "None on" still reads when nothing is on. Clear all removes everything
the row shows, the soil pH included. If the app's own filter survived "Clear all",
the reader would see fewer plants than the catalogue holds and no chip to explain
why.

**The keyboard is never dropped.** Three controls remove themselves when used: a
chip, an empty state's offer, and Clear all (hidden once nothing is on). Each
dropped keyboard focus where Qt put it, the next control in the window, which
live was the map toolbar's "# Grid". A chip now hands focus to the chip that takes
its place, or to Filters; Clear all to Filters; an offer to the plants that came
back. **Tab follows the screen**: chips and offers are made after their window,
and Qt appends such widgets to the end of the tab chain, after the plant list
(measured live: Filters → Clear all → Order → the list → the chips → the offer).
Now it runs Filters → chips → Clear all → Order → offers → the list. Chips are
rebuilt only when what is on changes, so typing does not pull a focused chip out
from under the keyboard.

When anything restricts the list, the count says how much: "339 of 424 plants".

### An empty result names what emptied it

When nothing passes, the picker re-runs the search once without each restriction
that is on: each facet, each quality, the search text and the soil pH. It offers
the ones that would bring plants back, most first. On the example design, with
Type: Sedge ticked and "aster" typed:

    No plant passes all of these together. Remove one:
    [Clear the search "aster" (18 plants)]
    [Remove "Type: Sedge" (16 plants)]

Tick Pollinator Support and Bird Food as well and only the second offer is left
("(15 plants)"). That is right: no sedge is listed as a pollinator plant, so clearing
the search alone still leaves nothing, and an offer that brings nothing back is
not made. A search alone that matches nothing reads "No plant's name or role
contains "zzzz"". If no single removal helps, the panel says the combination is
doing it, and offers Clear all. The searches run only when the list is empty: at
most nineteen, over 424 rows. Which restriction emptied the list and what removing
it brings back is answered in the Qt-free vocabulary (`plant_filters.what_emptied`,
over `filters_on` and `without`). The picker supplies the search and draws.

### The soil pH, as a filter you can see and untick

The app still turns it on when a pin's soil arrives, as V1.67 decided. It is now
named in three places: as a chip, "Your soil: pH 6.5 ×"; as a toggle in the filter
area beside the qualities, labelled the same, so it can be ticked back on; and in
the count. The tooltip says what the comparison rests on: "an estimate for the
area, not a measurement in your yard", and how many plants it is hiding from this
list now ("It is hiding 3 plants from this list" on the example, at pH 6.5).
Unticking holds for the session, so a soil re-fetch or a reloaded project does not
switch it back on. The picker owns the value now (`PlantPicker.set_soil_ph`).
`set_extra`, its only caller gone, is removed.

**It leaves with the site.** Nothing had ever turned it off. A new design reset the
zone and the pin's region but kept the last site's pH; removing the pin dropped its
soil data but kept `soil_ph` in the design and kept filtering; opening a design with
no pin kept whichever pH came before. Silent, that was a list quietly short of
plants; as a chip it would have been a design with no site saying "Your soil: pH
8.0". All three now clear it (`app._on_new`, `app._load_from_path`,
`map_events._on_site_pin_removed`, which also drops `soil_ph` and `soil_texture`
with the rest of the pin's data).

## Found on the way

- **The stale label's cause** (above). The fix stops any current item, not just
  these three inputs, so a fourth unknown path cannot bring it back.
- **The scroll wheel was stolen by every filter in the panel.** It showed up as
  the first of the three paths. It is fixed by the same change.
- **The pH ranges have no provenance.** All 424 rows carry one, 102 of them the
  same 5.5–7.5. Whether they are measured, transcribed from a reference or
  defaulted cannot be told from the data. That is a data question, not this step's.
  It is recorded here so the next person does not take the filter for precise. (F201,
  opened.)
- **The picker had its own FlowLayout.** V3.00 wrote one into `plant_picker.py`
  without noticing `src/flow_layout.py`, written for the placement bar in V2.98.
  The copy laid out hidden widgets as if they were there, which the soil toggle
  (hidden until a site has a pH), "None on" and Clear all would have shown as gaps.
  The copy is deleted; the picker uses the shared one.
- **Long tooltips ran across the screen.** Qt word-wraps a tooltip only when it is
  rich text, so the soil pH's, three sentences, was one line 1,340 px wide on a
  1,366 px screen, over the map. The picker's tooltips go out wrapped
  (`filter_status.wrapped`); a screen reader is given the plain words.
- **The keyboard fell onto the map's toolbar, and Tab reached the chips last**
  (above, under the chips). Both measured live, both fixed, and each test fails
  with its fix taken out.
- **The soil filter outlived its site** (above): a new design, a removed pin and a
  design opened without one all kept it. Fixed, with a test of each through the
  real window. **Left alone**: a pin moved to where the soil fetch finds no pH keeps
  the old one, because the site panel keeps all of the old pin's data in that case
  and the pH is one field of it; that is the site data's lifecycle, not the filter's.
  And undoing a pin's removal brings the pin back without its soil, as it always
  has, because the undo snapshot holds the pin and not the fetched data.
- **A test's combo had been kept alive by accident.** `test_plant_panel_smoke`
  built a combo with no parent inline and read an item from it. V3.00's widget
  connected a lambda that closed over the combo, a reference cycle that kept it
  alive; V3.01 connects a bound method, which PyQt holds weakly, and the combo was
  freed before the item was read. Every combo the app makes has a Qt parent; the
  test now holds its own.

## Left alone, on purpose

- **Whether the soil pH filters at all.** The measurement argues for ranking, like
  "Recorded near this site", rather than hiding. That reverses an owner decision
  from V1.67, so it is the owner's call, raised in the reply. This step makes the
  filter seen and removable, which the backlog row asked for.
- **The Directory and the builder do not get the soil filter.** Neither has a site,
  and giving them one is a different question from making a filter legible.
- **The community library's facet dropdowns** get the stale-label and wheel fixes,
  because they share the widget. They do not get faces or the combine line: their
  vocabulary is the community facets, and step 6 (F196) rebuilds that panel.
- **The search text is not a chip.** The search box already shows it and has its
  own clear button. It does appear in the empty state, because it is often the
  thing doing the emptying.

## How it is checked

- `tests/test_plant_filters.py`: the face and phrase for one, two and three
  values under each rule, in the facet's order however they arrived; the combine
  line; `filters_on`, `without` and `what_emptied` against a fake search; the soil
  words.
- `tests/test_filter_widgets.py` (new): the three inputs that made the stale
  label, each now leaving no current item and the placeholder after unticking;
  the wheel is passed on; ↑, ↓ and Space open the list; the combine line cannot be
  ticked, is not counted and is not given a box by `set_checked_keys`.
- `tests/test_plant_picker.py`: chips appear, remove their own filter and nothing
  else, and hand focus on; Clear all clears the soil pH and hands focus to
  Filters; an offer hands it to the list; Tab follows the screen; the empty state
  names the filter that emptied the list, with the count removing it gives; the
  soil pH is on, shown, removable, stays off after a re-fetch and can be ticked
  back, and its tooltip wraps.
- `tests/test_app_smoke.py`: a fetched soil's pH reaches Browse as a chip through
  the real window's path (`soil_flow.apply_soil_site_fields`), and leaves with the
  pin, with a new design and with a design opened without a pin; both lifecycle
  tests fail with the fix taken out. They put the shared window back as they found
  it: the first draft left the design marked changed, and the class's teardown hung
  on "You have unsaved changes. Exit anyway?", a modal nobody answers offscreen.
- Live, under Xvfb at 1366 × 768 with real input (xdotool): the wheel over the
  Type box, Space and Return in its list, and an untick by click, on the real
  Browse panel; the chips; the empty state by mouse and by keyboard alone; the
  soil chip's tooltip and removal; the Plant Directory's wide layout. The AT-SPI
  tree was read for each control.

| | V3.00 | V3.01 |

| Space on Shrub, Return, then untick by click | "● Shrub", nothing ticked | "Any type", no swatch |

The tab order and the dropped keyboard (above, under the chips) were measured on
this increment's own first build, since V3.00 had no chips or offers, and fixed
before it shipped.

The lost row is the soil chip: the example's two app-set filters fill the line and
push Clear all onto its own. It is the filter V3.00 left silent, so the row is
the cost of saying so. On a wider panel they fit one line.

The soil pH filter, as the example's 6.5 shows, is often mild; the table under
*What was wrong* is what it does on limy soil.

**The suite**, in this container, as CI runs it: 4,229 tests (V3.00: 4,184), 0
failed, 19 skipped (V3.00's reasons: bpy 7, rasterio 5, pypdf 3, and one each for
the PyQt6 import order, the nDSM backend, running as root and the shallow clone),
`RESULT: OK`. That run preceded the soil filter's lifecycle fix; after it, every
module that reaches the changed code ran again (`test_app_smoke`, now 26 with the
two lifecycle tests; `test_graduation`, `test_saves`, `test_plant_picker`,
`test_architecture_guard`, `test_start_menu`, `test_project_store`: 180), 0 failed.
`validate-data`: clean, its 113 warnings the existing data debt.

## What could not be verified here

- **What a screen reader says.** The AT-SPI tree was read directly: names, roles,
  the rule rows and the empty state's offers are there. No screen reader (Orca,
  NVDA, VoiceOver) was run, so the order and wording it speaks are not checked.
  That is F195's next step.
- **macOS and Windows.** The keypad modifier macOS puts on arrow keys is allowed
  for, but no Mac ran it. macOS styles never scrolled a combo with the wheel, so
  that path to the stale label existed on Linux and Windows only.
- **A real soil fetch.** The live soil chip came from the example design's cached
  pH; the pin → fetch → chip path is tested through `soil_flow` with a constructed
  result. No SoilGrids response was fetched here.
- **The empty state's text at other widths.** It wraps; it was looked at in the
  437 px panel and the Directory's 1,300 px window. In the Directory the offers
  stretch the full width, which reads oddly but was left.
- **Whether Clear all should take the soil pH with it** is a judgement, argued
  above, not a measurement. So is keeping the filter on by default.
