Status words: ☐ open · ◐ in progress (say who and where) · ☑ done (say the
commit). **One release per branch** (CLAUDE.md): every push to a `V*.*` branch
builds and publishes installers, and the in-app updater only offers a *new*
version number, so a branch is pushed when its piece works, and the next piece
starts the next branch (`V3.10`, then `V3.11`…), never more work on a pushed
one except a fix.

## How to pick this up

1. Read `CLAUDE.md` (the branch convention, the plan rule, "How to test this",
   "Explain every command"). The owner is learning the tooling: every command
   handed to them is explained.
2. Get the branch: `git fetch origin refs/heads/V3.09:refs/remotes/origin/V3.09`
   then `git switch V3.09` (never `git pull` a V-branch; CLAUDE.md says why).
   For a new piece, branch the next number from the last pushed one.
3. **Testing budget (the owner's rule since V3.07): halve it.** Run the
   modules you touched plus `tests.test_architecture_guard`; run the whole
   suite at most once per release, or let CI run it on the push
   (`.github/workflows/tests.yml` runs on every `V*.*` push). A subset that
   includes `tests.test_app_smoke` must list `tests.test_viewer_controls`
   first, or the window's tests skip.
4. Tick the row, add the commit, and push with `git push -u origin HEAD`.
5. End with a **How to test this** for the owner (CLAUDE.md).

## F206 — a community shown as a plant is

The owner: *"I quite like the way the 'plants' now show up in an adjacent 'pop
up' and would like the same for plant communities for ease of scrolling,
visibility and use. Selecting a plant community can show the pictures of the
plants in the community in the pop up (not too big as I want it to be mostly all
visible in one go) along with the description of the community and the ability
to drop down into individual descriptions of the plants."*

### Simple version (T2, V3.09)

- **Where.** The plant page's frame over the map's right edge
  (`src/species_flyout.py`, V3.00) shows a community too. A new
  `src/community_page.py` builds the page; the flyout holds both pages and shows
  one at a time.
- **What it shows, top to bottom.** The community's name and ✕; one line of
  facts ("8 plants · Full Sun · Mesic", `polyculture_panel.community_facts`,
  F196); **Place this community**; the members as **small photographs in a
  grid**, three across, about 96 × 64 px each with the name under, so most
  communities fit on one screen; the description (the pattern card the panel
  already writes, `pattern_language.pattern_card_html`).
- **Drop down into a plant.** A click on a member opens that plant's page in
  the same frame, with **◀ Back to <community>** above it.
- **When it opens.** A finished click or an arrow onto a community in
  Placement › Communities, when not placing, exactly as the plant page opens
  from Plants (the list's `choose` gesture, `src/place_action.py`). While
  placing, the list is a palette and no page opens (V2.99's rule); arming the
  map closes the page. ✕ or Esc closes it.
- **Photos.** From the plant rows' `image_url` through `image_cache`; one not
  cached yet is fetched by the Plants list's warmer
  (`PlantListModel.warm_photo`) and drawn when `imageReady` says so. No photo:
  the plant's type colour as a swatch and its name, never an empty box.
- **Left as it is.** The panel's own member rows and description stay until the
  owner has used the page (T9): removing them is a decision, not a cleanup.

### Fuller version (T9, later)

- Retire the panel's card once the page is in use (as V3.00 retired the
  plant card), giving the list the panel.
- Two communities side by side (F196 made them comparable in the list).
- Edit from the page (open the builder on this community).
- The community outlined on the map while its page is open (F202).

## F207 — existing buildings and trees, read off the map and the satellite

The owner, on Site › Features: *"a scan of both the map layer and the satellite
layer to work in synchronicity to provide an accurate placement of existing
buildings and trees … that can then be useful in the 3D view as well as the
birds eye designers view."*

### What exists (V3.08)

- `src/osm_features.py`: OpenStreetMap buildings and trees for a box
  (`fetch_existing_features`, `bbox_from_boundary_or_pin`,
  `filter_to_boundary`, `add_features_to_project`); Site › Features imports
  them all at once, with no review.
- `src/building_store.py` + `src/building_downloader.py`: an offline pack of
  OSM building footprints by region.
- `src/footprint_extract.py`: the seam for extracting footprints from imagery
  (`set_extractor`); the nDSM backend (`src/footprint_ndsm.py`) works from a
  surface model, with heights.
- Site › Features › *Satellite alignment*: a manual nudge of the Esri imagery,
  cosmetic only.
- Hand drawing and marking of trees and buildings.

### Simple version (T4, V3.10): *Scan this area*, then review

1. **Scan.** One button on Site › Features, *Scan this area*: the boundary's
   box (or 60 m round the pin) from OSM, and from the building pack when it is
   downloaded, off the UI thread (the existing import's worker).
2. **Review over the satellite.** The finds are drawn on the map in a
   proposal colour, over the satellite layer (switched on for the review), and
   listed with a tick each: *Building, 9 × 12 m, 6 m tall (OSM)*, *Tree,
   crown 5 m (OSM)*. Untick what is not there any more (a felled tree, a
   demolished garage); the map shows the change.
3. **Add.** *Add the N ticked* puts them in the design as one undo step, through
   `add_features_to_project`, so shade, 3D and the 2D map get them as an import
   does today. Things already in the design are not proposed twice
   (`_too_close`).
4. **Alignment, said.** If the satellite has been nudged, the review says by how
   much; a large nudge is the hint that the imagery, not the buildings, is off.

What it does not do: read anything off the satellite pixels. That is T7, and it
has a licensing question in front of it.

### Heavier versions

- **T6 · Open building footprints.** Microsoft's Canadian Building Footprints
  (ODbL, roof outlines traced from imagery, every province) cover buildings OSM
  does not have, which outside the big cities is most of them. One province's
  file is large (Alberta is on the order of a gigabyte unpacked), so it belongs
  in the offline-pack pattern (`.claude/skills/offline-packs`), downloaded by
  region on request, never shipped. Heights are not included; the review asks
  for one or uses the type default.
- **T7 · Lining the satellite up automatically.** Measure the offset between the
  imagery and the building footprints (edges of the roofs against the
  outlines) and apply it as the nudge. **Licensing first:** the satellite
  layer is Esri World Imagery, whose terms cover display; reading its pixels to
  derive data is a question for the terms, and the answer decides whether T7 is
  done on Esri tiles or only on imagery the owner has the rights to (their
  drone photo, a municipal orthophoto under an open licence). Ask the owner
  before building it.
- **T8 · Tree crowns from the owner's own imagery.** A drone or phone scan
  already comes in (`src/scan_import.py`, the nDSM path), with heights. For a
  plain photo with no heights, a vegetation index (green over red and blue)
  finds canopy pixels with numpy alone; crowns are the connected patches,
  vectorised to rings and offered through the same review as T4. A segmentation
  model (Segment Anything) is the heavy end: a large download and a torch
  dependency the packaged builds do not carry, so it stays optional behind
  `footprint_extract.set_extractor`, never required.
- **Municipal data.** Edmonton and Calgary publish tree inventories and
  building footprints under open licences; a city source beside OSM is the same
  shape as T6.
