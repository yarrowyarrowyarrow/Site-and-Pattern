# V3.15 — One click updates an installed Windows copy (F228)

## What was asked

The owner, with a photo of a friend's screen: *"Why does my friend get this warning
when trying to update the version on his computer while I don't seem to have this
issue. We both use the check for updates button."* Then, once the answer was in:
*"Can we make it so everyone has it as easy as I do. Ie. A 'one click' update
without hassle."*

## What was wrong

**The photo.** NSIS's *Error opening file for writing: C:\Program Files
(x86)\Site & Pattern\SiteAndPattern.exe*, with Abort / Retry / Ignore, and Site &
Pattern still open behind the installer, its map of Edmonton on screen.

**Windows does not let a running program's files be opened for writing.** The
installer's first file is the program itself, so it stopped there.

- **The app started the installer and stayed open.** `update_flow._open_installer`
  called `os.startfile(path)` and showed *"Click through it to update in place …,
  then reopen Site & Pattern. You can close this older copy now."* That message
  appeared at the same moment as the installer, said the steps in the wrong order,
  and made closing sound optional.
- **The installer never checked.** `installer.nsi` went straight to `File /r`. The
  build script already knew about this lock: `build_installer.bat` kills running
  copies before a rebuild because "without this, rmdir fails". The installer had
  no equivalent.
- **Why the owner never saw it.** The owner runs from a source checkout, where the
  same button runs `git checkout` and offers a restart. Python does not hold its
  `.py` files open, so nothing is locked. The friend runs the installed copy, where
  the button downloads and runs the installer. Same button, two mechanisms.

**Measured, by compiling the shipped script** with makensis 3.09 against a
stand-in bundle:

- `File /r` writes the folder's files before its subfolders, and the bundle's
  root holds only `SiteAndPattern.exe`. So the error came on the very first
  file, and **Abort at that dialog changes nothing**.
- *warning 6020: Uninstaller script code found but WriteUninstaller never used -
  no uninstaller will be created.* The Start menu's **Uninstall** shortcut has
  pointed at a file that was never created, for every release.

**Ignore was the dangerous button.** The app's Python code lives inside
`SiteAndPattern.exe` (PyInstaller's PYZ), while `version.txt` is a loose file in
`_internal`. The DLLs there are locked too. Skipping every locked file while
writing the rest leaves the old program reporting the new version.
`_frozen_check_for_updates` compares only that version, so the friend would have
been told *up to date* from then on.

## What was decided

1. **The app hands over and closes** (`update_flow._install_windows_update`):
   - It settles unsaved work first: **Save and update** (the default), **Update
     without saving**, or **Cancel**.
   - It starts the installer with `/UPDATE /D=<the folder it runs from>` through
     `os.startfile(arguments=…)`, which is ShellExecute, so Windows shows its
     permission prompt.
   - It closes every window (`QApplication.closeAllWindows`). Qt keeps the
     process, and its files, alive while any window is open.
   - Answering No to Windows leaves the app open, still unsaved if it was,
     with *"nothing has changed"*.
   - The offer says beforehand that the app will close and reopen, and that
     Windows will ask (*choose Yes*).
2. **The installer has an update mode** (`installer.nsi`, `/UPDATE`):
   - It skips the folder and finish pages.
   - It waits up to a minute for the program's files to be free, then asks in
     words (Retry / Cancel).
   - It replaces `_internal` rather than layering over it, so a module the new
     version dropped cannot stay importable.
   - It closes when done and opens the app again as the person who ran it.
   - Cancel leaves the install exactly as it was.
3. **Run by hand, the same check asks at once.** Every copy older than V3.15
   still starts the installer this way, so that path matters for one more
   update. A finish page offers **Run Site & Pattern**.
4. **`AllowSkipFiles off`.** A file that cannot be written is Abort or Retry,
   never Ignore.
5. **An uninstaller that exists, and is listed in Settings → Apps.** It removes
   only what the installer put there. The uninstall section that had never run
   did `RMDir /r "$INSTDIR"`. Writing the uninstaller as it stood would have
   armed that: a folder typed on the folder page, such as `C:\Tools`, would have
   gone with everything in it.
6. **The folder is remembered** (`InstallDirRegKey`), so a later manual install
   proposes it. An update ignores it, because `/D=` names the running copy's
   own folder.
7. **Readable versions in the dialogs.** They had said *Latest: release-V3.15*;
   the prefix exists for git (`github_releases.version_label`).

### Why the app passes its own folder

`InstallDir` is `$PROGRAMFILES\Site & Pattern`. A copy installed anywhere else
would be "updated" by a second copy appearing in Program Files, while the
shortcut kept opening the old one. `/D=` must be the last argument, unquoted,
spaces and all; `installer_update_arguments` builds it that way, and a test pins
it.

### Why the installer reopens the app through Explorer

The installer runs as administrator, and a program it starts with `Exec` would
too. When someone else's password answered the Windows prompt, that program runs
as *that* account, with that account's data folder. Explorer already runs as the
person at the keyboard, and `explorer.exe "<path to exe>"` opens the program the
way a double-click does. If that ever fails, the app simply doesn't reopen and
the person opens it themselves; nothing is lost.

### Why a write test, not a process list

The installer asks whether `SiteAndPattern.exe` (and the web engine's
`QtWebEngineProcess.exe`) can be opened for writing. That is exactly what `File`
needs, it reads the same in every Windows language, and it needs no plugin.
Chocolatey's NSIS ships none of the process plugins.

## Verified

- **Compiled with every warning an error** (makensis 3.09, here and now on CI:
  `tests.yml` installs `nsis`). The shipped script fails that test with warning
  6020; this one passes.
- **Run under Wine 9.0** with stand-in programs, since there is no Windows
  machine here:
  - A fake *old app* that holds its own file, as a running program does, started
    the real installer through ShellExecute with the app's arguments, then took
    6 s to close.
  - The installer touched nothing until the old copy had exited (6.6 s). It then
    removed the old version's stray module, copied the new files, wrote the
    uninstaller and the Settings → Apps entry (DisplayVersion read from
    `version.txt`, CRLF and all), and opened the fake *new app* through Explorer
    at 7.3 s.
  - A copy in `C:\Apps\My Site & Pattern (copy)` was updated in place and
    reopened from there. The default folder was untouched, though the registry
    pointed at it.
  - With the app open, a manual run asked at once. Update mode waited the full
    minute and then asked. Cancel left every file byte-identical in both cases.
  - The uninstaller removed its files, shortcuts and keys, and left a file of
    the user's and the folder holding it.
  - Installed into a folder holding another program's `_internal` (no
    `SiteAndPattern.exe` there), the installer left that program's files alone:
    `_internal` is replaced only where Site & Pattern is installed.
  - A clicked-through manual install showed **Run Site & Pattern** (the `&`
    drawn correctly) and opened the app from Finish. The desktop shortcut
    appears on a manual install, and is not recreated by an update when the
    person had deleted it.
- **The two dialogs a person can meet**, drawn by Wine:
  [`V3.15-installer-under-wine.png`](../img/ui/V3.15-installer-under-wine.png)
  (left: update mode after the wait; middle: a file held by another program,
  Retry / Cancel only; right: the finish page).
- **The app side** (`tests/test_windows_update_flow.py`): the arguments, the
  save / don't save / cancel / failed-save / declined-prompt paths, the offer's
  wording. These fail on the V3.14 controller.

## What could not be verified here

- **Real Windows.** Wine implements share modes and ShellExecute faithfully
  enough for the logic, but it is not Windows:
  - The lock a running PyInstaller exe holds was stood in for by NSIS's own
    open file handle. Windows' image lock is stronger, not weaker.
  - Explorer's hand-off to the already-running shell is the part most worth
    seeing on a real machine.
  - The first real test is the friend's next update.
- **The Windows prompt's *No*.** `os.startfile` raising `OSError` (WinError 1223)
  is the documented ShellExecute behaviour, tested with a stub.

**Trying it on Windows without waiting for V3.16.** The one-click path runs only
when a version newer than the installed one exists, except through *Help →
Switch to a specific version…*: picking the installed version (listed as
`release-V3.15`, unmarked, because of the found-not-fixed comparison below)
reinstalls it through exactly this path.

## The transition

Every copy older than V3.15 starts the new installer the old way: the folder
page, then this version's *"still open … click Retry"* in place of the cryptic
error, then the finish page to reopen. **One last update by hand; one click from
V3.15 on.**

The other direction: *Switch to a specific version* back to one older than
V3.15 runs that version's installer, which ignores `/UPDATE` but honours `/D=`
(NSIS reads it, not the script). It shows its pages, finds the app already
closed, and installs in place; the person reopens the app themselves.

## What is not being done

- **macOS stays drag-to-Applications** (opened as **F229**). Replacing a running app works on macOS,
  so there is no error, only steps. One click there means a helper that waits for
  the app to quit, mounts the image, swaps the bundle with a rollback and reopens
  it. That should be tried on a real Mac before it ships, and nothing here can.
- **The Windows permission prompt stays** (opened as **F230**), one Yes per update, because the
  program lives in Program Files. Removing it means a per-user install
  (`%LOCALAPPDATA%\Programs`, no administrator). That needs a migration out of the
  existing folder: pinned taskbar icons point at the old path and would keep
  opening the old copy. It is the owner's decision.
- **Program Files (x86) for a 64-bit program** (`$PROGRAMFILES` in a 32-bit
  installer): harmless, and moving it is the same migration.
- **Code signing** would turn the yellow *Unknown publisher* prompt blue, and
  costs a certificate.
- **Found, not fixed:** *Switch to a specific version* compares `r.tag ==
  current`, which never matches a `release-` tag. Its "(current)" marker and
  "already on" check have been silent since V2.80. That is harmless (it offers
  a reinstall) and outside this change.
