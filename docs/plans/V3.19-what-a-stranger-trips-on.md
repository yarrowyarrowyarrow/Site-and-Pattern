### The map page (QF-6, QF-8, QF-14, QF-18)

1. **[major] QF-14: Closing a plain outline with a double-click is refused as 'crosses itself' when the second press moves a pixel**
   - *Where:* html/map/02-boundary.js:12-28 adds a corner for each click of a double-click: both clicks reach onMapClick, and only the first point has the 12 px close test. 01-core.js:814-823 then finishes on dblclick. src/outline_check.py:51-60 corners() drops only EXACT repeats before LinearRing.is_simple (outline_check.py:69). A second press 1-2 px from the first leaves a tiny side that runs back along, or across, the side before it, and is_simple is false for that.
   - *What goes wrong:* I ran the real page in headless Chromium at zoom 20, drew a rectangle by clicking 3 corners, then double-clicked the 4th with the second press 1 px to the right. The page sent 5 corners, and outline_check.crosses_itself returned True. The box then says 'The outline crosses itself, so it was not kept. Draw it again, clicking the corners in order around the edge.', which is untrue for someone who did click in order. For a 10 m square, 8 of the 24 offsets within +/-2 px refuse the outline. That window is inside the double-click distance on Windows (4 px) and in Qt. Trackpad taps often move this much. Before V3.19 the same draw was stored with an invisible sliver. Now the first step of the homeowner path fails at random. The tests cover only an exact repeat (test_a_repeated_corner_is_not_a_crossing).
   - *Suggested fix:* In handleBoundaryClick, ignore a click within a few pixels (for example 4 px) of the last corner. A pixel test works at every zoom; a fixed distance in metres does not. Optionally, corners() could also merge a corner within a few centimetres of the one before it. Add a test: a square closed by a double-click whose second press is 1 px right and 1 px up is stored.

2. **[minor] QF-14: On a reopened or undone outline, dragging the first corner can be refused when the same drag on a freshly drawn outline is kept**
   - *Where:* src/project.py:233-235 sends the saved, closed ring to the page. persistence.py:612 does the same for every open and every undo/redo redraw. So the page's b.points repeats corner 0 at the end, and enterBoundaryEditMode (02-boundary.js:473-481) makes n+1 handles; the copy's handle is on top. Dragging it moves only the copy, which leaves the old corner as an extra point (a spur). map_events.py:390-394 now refuses that ring as crossing.
   - *What goes wrong:* In the real page I loaded a four-sided outline that is not a box, the way project_to_map_data sends it, entered edit mode, and dragged the first corner 60 px right and 40 px down. The page sent 5 points, crosses_itself=True, so the edit is refused with 'That move would make the outline cross itself, so the corner went back where it was.' The identical drag on the same outline freshly drawn (4 points) is accepted. A person who opens a saved design, or presses Ctrl+Z once, and drags that corner outward is told their ordinary move crosses the outline. A retry works only because the refusal removed the copy. The builder left the duplicate alone on purpose; the new refusal turns that silent spur into a false message.
   - *Suggested fix:* Drop the repeated closing corner where the page receives a boundary: in loadBoundary (05-features.js), or in project_to_map_data's boundary points. That removes the doubled handle and the spur, and makes QF-8's zero-length side impossible at the source. The handle count then equals the number of corners, which is what the user expects.

3. **[minor] QF-6: Moving to the next tile host from inside Leaflet's 'load' event throws a TypeError each time**
   - *Where:* html/map/11-map-furniture.js:188-189 calls next() synchronously inside the layer's 'load' handler. next is 01-core.js:551-553, _useBasemap(i+1), which removes that layer, so layer._map becomes null. Leaflet 1.9.4's _tileReady reads this._map._fadeAnimated straight after fire('load') (the vendored leaflet.js: 'this.fire("load"),b.ielt9||!this._map._fadeAnimated?...'). The old 8-error path removed the layer inside 'tileerror', before the early return on a missing tile, so it never hit this.
   - *What goes wrong:* In headless Chromium, offline, a 240x200 map (fewer than 8 tiles, so the new path runs first, as it does during the app's 100x30 moment when the window first shows) logged 'Uncaught TypeError: Cannot read properties of null (reading '_fadeAnimated')'. map_widget.javaScriptConsoleMessage sends this to stderr and the log as [js:ERROR].    - *Suggested fix:* Defer the hand-over until Leaflet has finished its own dispatch, for example `if (verdict === 'next') setTimeout(next, 0);` (or L.Util.requestAnimFrame(next)). Add a probe or node assertion that no error is thrown when the hand-over happens.

4. **[minor] QF-6: After the connection returns, the message and the grey map stay until the map is moved; a small pan leaves the failed squares blank**
   - *Where:* 11-map-furniture.js:213 hides the box only on a 'tileload'. Leaflet never asks again for a tile that failed: GridLayer._update skips any key already in _tiles. Nothing listens for the connection coming back.
   - *What goes wrong:* Someone working offline reconnects Wi-Fi and looks back at the app. The box still says 'The map needs an internet connection to load.', which is now false. The map stays grey.
