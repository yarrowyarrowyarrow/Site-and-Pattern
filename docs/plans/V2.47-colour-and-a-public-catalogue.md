# V2.47 — Flower colour, and the catalogue on the open web

## Context

A competitor read, on the author's request: [BloomsEye
Studio](https://studio.bloomseye.com/) — a browser-based ornamental garden
designer with a content site attached. The site itself was unreachable from this
session (egress policy blocks `bloomseye.com`), so the comparison was assembled
from search-engine indexing of their own marketing copy, a species page, the
guides index, and the terms and privacy pages. **That limitation is recorded
here because it bounds the finding:** we have their data model and their URL
shapes, not their designer's toolbar.

Two gaps came out of it that are worth acting on, and the author picked both.

**1. Colour.** They filter by flower colour and sell *"preview its colour month
by month."* We hold `flower_color` as a hex on 390 of 434 seeded species, render
lit florets from real petal morphology in 3D — and `search_plants` takes thirty
parameters, **none of them colour**. The data has been sitting there since
schema v31 (V1.90) with nothing to press. This is the same shape as the V2.41
finding (sixteen filters that worked the whole time with nothing to press) and
the V2.37 dead-control bugs.

**2. Distribution.** Their `/plants/`, `/plants/blooming-in/september/` and
`/plants/<slug>/` pages are a search-landing funnel into the designer. Our public
surface is a GitHub README. The bitter part is that **F90 already built the
content** — the Plant Directory has thirteen filters, species pages with photo
credits, sourced ranges carrying occurrence counts and confidence, and every
documented animal with specialists flagged — and it is locked inside a desktop
binary. We built the encyclopedia and shipped it as an `.exe`.

## What I measured

### Flower colour is a small, clean, HSV-separable palette

390 of 434 seeded species carry a `flower_color`; the 44 that do not are exactly
the 43 with `flower_form = 'none'` plus one gap (MacKenzie's Hedysarum, form
`pea`, colour blank). Only **23 distinct hexes** are in use. Grouped by HSV:

| Bucket | n | Hexes |
|---|---|---|
| straw | 79 | `#cbbd80` |
| yellow | 77 | `#f2c11e` ×69, `#f0a818` ×5, `#a89a3c`, `#f2c53d`, `#f2c200` |
| white | 75 | `#f2f2ea` ×73, `#f4f0e6`, `#f5f5f0` |
| purple | 61 | `#8e6fc4` ×50, `#b07fc0` ×10, `#c9b8e0` |
| pink | 43 | `#e58fb0` ×34, `#d6457e` ×9 |
| cream | 26 | `#ece6c8` |
| blue | 16 | `#6f8fd6` ×13, `#7e7fc4` ×3 |
| red | 8 | `#d6453a` ×6, `#8a3a44` ×2 |
| orange | 3 | `#e07020` ×2, `#e2571e` |
| brown | 2 | `#7a5230`, `#8a6f3c` |
| *(none)* | 44 | `''` |

### The largest bucket is not a flower colour

**All 79 `#cbbd80` are grasses, sedges and rushes, and all 79 have
`flower_form = 'plume'`.** That hex is the wind-pollinated default: Poaceae,
Cyperaceae and Juncaceae are anemophilous and do not advertise. Dropping those 79
into a bucket labelled "yellow", next to a black-eyed susan, would be exactly
the false precision P9 forbids — the app would be claiming a flower colour where
the data means *there is no showy flower*.

So they get their own bucket, named for what it is: **"Straw / green (grasses &
sedges)"**. It stays *selectable*, because someone designing for winter texture
wants precisely that set — but it never masquerades as a bloom colour.

### The other boundary that needed care

`#c9b8e0` is pale lilac at saturation 0.18 and value 0.88. A naive
"low saturation + high value = white" rule swallows it. The white threshold is
therefore saturation ≤ 0.12, which admits only the three genuine off-whites and
leaves `#ece6c8` (0.15, warm) as *cream* and `#c9b8e0` as a pale *purple*.

## Decisions

### Colour is classified in Python, not matched in SQL

`flower_color` is a single column, so `WHERE flower_color IN (…)` would work
today — by enumerating the hexes each bucket currently contains. It would also
silently stop matching the first time a seeder writes a hex nobody enumerated.

The filter therefore runs as a **post-query pass, exactly like `_month_filter`**,
which is already in `search_plants` for the same reason: the stored value needs a
*parser*, not a comparison. That also means the classifier is one function, used
identically by the search layer, the directory facet and the static site — three
consumers that can never disagree about what colour a plant is.

### The taxonomic rule is primary; the hex rule is the backup

`classify()` checks `plant_type ∈ {grass, sedge, rush}` **before** looking at the
hex. That ordering is deliberate: "wind-pollinated families do not have showy
flowers" is a botanical fact and the *reason* for the straw bucket, whereas the
HSV band that also happens to catch `#cbbd80` is a heuristic. Encoding the
reason means a grass that acquires a brighter hex still classifies honestly.

### A plant with no recorded colour matches no colour

Same rule `_month_filter` already applies to bloom windows: *"we don't know what
colour this flowers"* is not the claim *"it flowers white"*. The 44 blank rows
drop out of every colour filter rather than defaulting into one (P9).

### The static site is a generator, not a server

`src/static_site.py` (page model, Qt-free) + `src/static_site_render.py` (HTML) +
a `build-site` CLI subcommand. Output is plain files: no build step, no
framework, no CDN — the same self-contained discipline the app already applies
to `html/`. It reads the same `plant_directory.species_entry` the desktop window
reads, so the web species page and the desktop species page are the same page
rendered twice, and cannot drift.

### The URL shapes are theirs; the pages that matter are not

BloomsEye proved the SEO shape and there is no reason to invent a different one:
`/plants/`, `/plants/<slug>/`, `/plants/blooming-in/<month>/`. To it we add the
two axes they cannot have —

- `/plants/colour/<colour>/` — the filter this increment builds, and the
  cheapest possible proof it works;
- `/wildlife/<slug>/` — **which plants feed this animal**, over the 361
  documented edges. Nobody else has this page. It is the whole argument of the
  app as a URL.

### Photographs: local cache first, remote fallback, credit always

Photos are open-licensed (CC0 / CC BY / CC BY-SA) and the licences oblige
attribution, which `image_cache.credit_line` already formats. The generator
copies bytes out of the local image cache when they are there and falls back to
the recorded URL when they are not, reporting both counts at the end of the
build. **A photo without an attribution is not emitted at all** — the rule the
3D dossier already follows.

## What this is deliberately not

- **Not a web port of the designer.** Rasters, DEM, soil GeoTIFFs and splat
  backdrops are not a browser workload. The directory goes to the web; the
  designer stays on the desktop. Stated so the omission reads as a decision.
- **Not a colour *palette adviser*.** "Your June is all yellow" is a real
  feature (it serves P13, and the data now supports it) but it is a design-side
  analysis, not a filter, and it belongs to whatever increment picks up the
  bloom-succession gap check.
- **Not a hosting or deploy step.** The generator writes a directory. Where it
  gets published is the author's call and needs no code.
- **Not new knowledge.** Same rule F90 set: every fact on every page already
  existed. What did not exist was a public URL to read it at.

## P12

The static site publishes the same fields the directory already surfaces —
horticultural and permaculture use tags, edible parts, documented ecological
relationships. **No ethnobotanical content is added, no field is relabelled to
imply any, and nothing about Indigenous plant use is inferred, aggregated or
made more discoverable by putting these pages on the open web.** Publication
raises the stakes on that rule rather than relaxing it: a page on the internet is
harder to withdraw than a panel in a desktop app.

## Verification plan

- `classify()` over all 434 seeded rows must reproduce the bucket table above
  exactly — asserted from the shipped JSON, so a reseed that changes a hex fails
  the test rather than silently re-bucketing a plant.
- The facet guard (`test_plant_directory.py`) already asserts every facet names a
  real `search_plants` parameter; the new facet is covered the moment it is added.
- The generator must build against the real database and produce a page per
  species, with no page containing an unattributed photograph.
- Every internal link the generator emits must resolve to a file it also wrote —
  a static site's characteristic failure is a 404 nobody notices.

## What actually happened

The colour half went in as planned — the measured bucket table above is
reproduced exactly by `classify()` and is now asserted against the shipped JSON,
so a reseed that recolours a species fails the build instead of quietly re-filing
it. The site half turned up five things the plan did not predict.

### A crash that had been shipping since F90

Building 439 species pages meant calling `species_entry` on every row for the
first time. Row 101, False Box, ships `hardiness_zone_min = '4?'`, and
`_zone_range` did `int(lo)`. **`ValueError`, page dead** — which means that
species could not be opened in the desktop plant directory *at all*, and had not
been openable since the directory shipped. One row in 434, so only a sweep would
ever have found it; the guard is therefore a sweep over every species, not a
case for that row.

The fix keeps the mark. `4?` is a botanist's "about four, not verified" and P9
says render the hedge rather than round it off, so the page reads `zone 4?–8`.

### The nav was one empty bucket away from a sitewide dead link

The header linked `plants/colour/yellow/` and `plants/blooming-in/june/`
directly. Against the real catalogue both exist, so the full build passed its
link check — and the fixture build, which has no yellow plant, produced a dead
link in the header of *every page*. Fixed by writing three hub pages
(`plants/colour/`, `plants/blooming-in/`, `plants/for/`) that are always
emitted, which the site wanted anyway. **The small fixture caught what the real
data hid**, which is the argument for having both.

### Thumbnails were bypassing the attribution rule

`_first_photo` gates the species page's hero image on having an attribution, and
the listing cards were reading `image_url` straight off the row. A CC BY
photograph obliges credit *wherever it is used*, and a card is a use. Every
thumbnail now goes through one gate (`photo_credit`), and the credit rides in
the image's `title` and `alt` because a card has no room for a caption.

### `SITE_NAME` was escaped twice

Stored as `"Site &amp; Pattern"` and then passed through `_esc` on the
`<title>` path but not the header path — so every page title read
`Site &amp;amp; Pattern`. Constants are now plain text and escaping happens
only at the point of use.

### The architecture guard fired, and was right

`static_site_render.py` hit 1012 lines against the 900 it was being opted in at.
Roughly 190 of those were a CSS string constant and a JavaScript string
constant. They moved to `html/site/site.css` and `html/site/browse.js`, which is
better independent of the line count: CSS embedded in a `.py` is CSS nobody can
lint, highlight or diff. `html/` is already bundled wholesale by the PyInstaller
spec, so frozen builds needed no change.

### Numbers as built

439 species pages, 86 wildlife pages (of 142 animals — the other 56 have no
documented plant and get no page), 11 colour buckets of which 10 are non-empty,
566 files, 10,257 internal links, **0 dead**. Build takes 3.7 s.

### The P12 decision, made rather than deferred

Scanning the free-text `notes` field for the publication risk found **43 rows**
carrying what reads as traditional medicinal and plant-use knowledge —
*"Traditional expectorant"*, *"Root harvested for respiratory medicine"*,
*"Traditional smoking-mix bark"*, *"Leaf tea is traditional for women's
health"*. This is pre-existing seed data, already visible in the desktop app,
so nothing was *added* — but publishing it is a materially different act, and
the hard rule says stop and raise it.

The default is therefore **notes withheld**, with `--include-notes` for when the
author decides otherwise, and an About-page paragraph saying plainly that the
omission is deliberate and why. The horticultural half of those notes — how a
plant spreads, whether it is toxic, where to buy it — is carried by structured
columns and publishes either way, so little of practical use is lost. **This is
flagged for the author rather than settled by me:** the deeper question is
whether that content should be in the shipped seed data at all, which is a data
decision, not a rendering one.

## What I could not verify

- **The competitor comparison that motivated this.** `bloomseye.com` and
  `studio.bloomseye.com` are blocked by this session's egress policy. Their URL
  shapes and filter axes come from search indexing of their own pages, not from
  loading them.
- **How the site looks in a browser.** No display in this container; the HTML is
  verified structurally (links resolve, every page is written, no unattributed
  photo, the browse script can find the cards it filters) rather than visually.
  Nobody has looked at the dark-mode palette on a real screen.
- **The photograph copy path.** This container's image cache is cold, so all
  321 attributable photos came out as links to their original URLs. The
  copy-from-cache branch is exercised by the code path but has not been run
  against a warm cache; the build reports both counts precisely so the operator
  finds out before publishing rather than after.
- **The suite's 12 errors are not mine.** 2777 tests, 12 errors, 365 skipped —
  every error is `ModuleNotFoundError: No module named 'PyQt6'` from
  `test_viewer_controls`, `test_creature_scale` and `test_learn_mode`, which
  import Qt inside test bodies instead of guarding at module level, so they
  *error* where the other ~156 widget tests *skip*. Confirmed pre-existing by
  running `test_viewer_controls` against a stashed tree: identical 4 errors.
  Worth fixing (a module-level skip guard) but not in this increment.
