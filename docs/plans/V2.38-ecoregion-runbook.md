# Ecoregion rebuild — the two steps that run on your machine

Everything else in the rebuild is built, tested and committed. These two steps
need open network egress, which the project's cloud sessions do not have: the
proxy answers **403 to CONNECT** for `api.gbif.org`, and the CEC atlas download
was always a manual one. So they run on your PC, and the output gets committed.

Neither is urgent. **Step 2 is the one that fixes Saskatoon Berry**, and it can
be run on its own — it does not depend on step 1, it just gets more accurate
afterwards.

---

## What is already done

| | |
|---|---|
| The vocabulary is the polygon file | Add a region by adding a polygon; the filter, the validator and the seeder all read it. No second list. |
| A site can be in two ecoregions | `lookup_ecoregions` returns all matches; the whole chain (detection → filter → community cross-link) carries a list. |
| Geography and moisture are separate axes | `riparian` / `wet_meadow` are conditions, not places, and no lookup can return one. |
| `plant_ecoregions` table (schema v59) | One row per species per region with the record count, a confidence band and the source. |
| Read-side synthesis | Derived rows override the heuristic tags; moisture niches carry through; a species with no derived rows keeps what it had. |
| Both scripts | Single-command, dry-runnable, and tested against injected fixtures. |

The catalogue behaves exactly as before until you run step 2 — the table is
empty, so every species falls back to its existing tags. Nothing is broken in
the meantime.

## Step 1 — real polygons (optional, do it when you feel like it)

The shipped polygons are **rectangles**. Five vertices each, drawn by hand in
V1.36 as a starter set. They put Edmonton in Aspen Parkland and Regina in Moist
Mixed Grassland correctly, but a site near any boundary is a coin flip.

```bash
pip install fiona shapely pyproj
```

1. Download **CEC Level III Ecoregions of North America** (shapefile) from
   <http://www.cec.org/north-american-environmental-atlas/ecoregions/>.
   Unzip it somewhere.
2. Check the licence terms and add a line to `docs/DATA_SOURCES.md` — that
   document's standard is that "are you allowed to have that?" has a checkable
   answer.
3. Run it:
   ```bash
   python scripts/prepare_ecoregions.py --shapefile /path/to/NA_CEC_Eco_Level3.shp
   ```
4. Open `data/ecoregions_canada.geojson` and sanity-check a few known points
   (Edmonton, Calgary, Regina, Saskatoon). `python -m unittest tests.test_ecoregion`
   asserts a dozen cities; **expect some to need adjusting** — Calgary sits on
   the prairie/foothills transition and the rectangles currently give it
   `fescue_foothills` by fiat.
5. Bump `_SCHEMA_VERSION` in `src/db/plants.py` and commit both.

**Adding BC, or anywhere else, is this step and only this step.** Add the CEC
names to `KEY_MAP` in the script, add display text to `DISPLAY` beside it,
re-run. The filter dropdown, the data validator and the range derivation all
pick it up from the file.

## Step 2 — per-species ranges from GBIF (this is the one that matters)

This is what fixes the reported bug. No account, no API key, no download to
find — just network.

```bash
# Try one species first. Prints, writes nothing.
python scripts/seed_ecoregion_ranges.py --species "Amelanchier alnifolia" --dry-run
```

You should see something like:

```
[1/1] Amelanchier alnifolia: 631 records → aspen_parkland=312(high), boreal_mixedwood=44(high), …
```

If that looks right, do the lot:

```bash
python scripts/seed_ecoregion_ranges.py
```

Safe to re-run and safe to interrupt — the file is checkpointed every 25
species, and the output is sorted and deterministic, so a second run's diff is
real change in GBIF rather than churn.

### If it says species COULD NOT BE FETCHED

Re-run it. That is the whole recovery:

```bash
python scripts/seed_ecoregion_ranges.py --resume
```

`--resume` skips species that already have rows and retries everything else. It
is safe to run as many times as it takes; each pass should have fewer failures
than the last. The script exits non-zero while any species is still unfetched,
so **do not commit until it exits 0** — a species missing because GBIF refused
is not a species that grows nowhere.

If it is still being throttled hard, slow it down and leave it running:

```bash
python scripts/seed_ecoregion_ranges.py --resume --sleep 3
```

### Then

1. Read the **"regions under the threshold"** list it prints at the end. Those
   are species sitting at one or two records somewhere — the cases worth a
   human's eye, which is why they are printed rather than dropped.
2. Bump `_SCHEMA_VERSION` in `src/db/plants.py` (so existing installs reseed).
3. Run the suite, then commit the data and the bump together.

The bump is one number and one comment. Open `src/db/plants.py`, find
`_SCHEMA_VERSION` (~line 226, at the end of a long changelog comment block),
and add your line above it:

```python
# v60 (V2.38): no DDL — reseed to pick up data/plant_ecoregions.json, the
# GBIF-derived per-species ecoregion ranges. Saskatoon Berry finally says
# aspen_parkland, with 312 records behind it.
_SCHEMA_VERSION = 60
```

The comment matters more than it looks: that block is how a later session
works out why a bump happened, and "no DDL — reseed to pick up …" is the
house phrasing for a data-only bump. Then:

```bash
python -m unittest discover -s tests
git add data/plant_ecoregions.json src/db/plants.py
git commit -m "Derive every species' ecoregion range from occurrence records"
git push -u origin V2.38
```

Without the bump nothing happens on an existing install: `init_db` only
reseeds when the stored schema version is older than `_SCHEMA_VERSION` (or the
plant count is under 100), so the new file would ship and never be read.

### What it will and will not do

- It derives **geographic ecoregions only**. `riparian` and `wet_meadow` are
  site-scale moisture niches and no coordinate can assert them, so those tags
  are left exactly as they are.
- It **never deletes a tag on its own authority**. Regions with records but
  fewer than three are printed, not silently dropped.
- A species it could not fetch keeps everything it had. Failing to reach GBIF
  must not read as "grows nowhere".
- Cultivated records (`LIVING_SPECIMEN` and friends) are excluded — a botanical
  garden is not an ecoregion.
- It only asks GBIF for records **inside the polygons' bounding box**. Anything
  outside is discarded downstream anyway, so downloading it was pure cost — and
  it was most of the cost. This is why the run is much shorter than the first
  attempt.

### What went wrong the first time, and what changed

The first version asked at ~3 requests/second and pulled every record worldwide
per species. GBIF started answering **HTTP 429** after 228 species — and the
script recorded each throttled species as having *no georeferenced records*,
which reads as "this plant grows nowhere". That is exactly the kind of
unsourced claim this pipeline exists to remove, arriving through the back door.

| | |
|---|---|
| A failure is not an absence | Reported separately, left out of the file entirely (so the species keeps its existing tags), and the run exits non-zero |
| Ask for less | Query bounded to the polygon bbox — a grass with 3,000 records worldwide has a few hundred in the prairie provinces; ten pages become one |
| Slow down and stay slow | 1s between calls, backing off 5/15/45/120s on a 429 (honouring `Retry-After`), and the slower pace persists for the rest of the run |
| Don't lose the work | Checkpointed every 25 species, and `--resume` picks up where it left off |

### The threshold, and why it is three

Two records is a coincidence: a misidentified herbarium sheet plus a garden
escape will do it. Three is the smallest number that is evidence of anything,
and it is reported as **low** confidence so nothing downstream mistakes it for
a range map.

| records in a region | confidence |
|---|---|
| ≥ 20 | high — a documented population |
| 8–19 | medium — consistent, thinly collected |
| 3–7 | low — present, barely |
| < 3 | not claimed (but printed) |

Raise it with `--min-records N` if the output looks noisy. Raising it too far
re-creates the original problem from the other direction: a real but
under-collected region dropping off the list, which is exactly how Aspen
Parkland lost Saskatoon Berry in the first place.

## How to tell it worked

```bash
python - <<'EOF'
from src.db.plants import get_all_plants
for p in get_all_plants():
    if p["scientific_name"] == "Amelanchier alnifolia":
        print(p["common_name"], "→", p["ecoregion"])
        for e in p.get("ecoregion_evidence") or []:
            print("   ", e["ecoregion"], e["occurrences"], e["confidence"])
EOF
```

`aspen_parkland` should be in that list, with a record count behind it.
