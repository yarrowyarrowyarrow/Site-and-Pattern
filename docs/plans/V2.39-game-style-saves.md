# V2.39 — saves you can find, in a list, without a file dialog

## The ask

> *"Saving a file should be more simple and similar to how game files are saved
> and loaded. There should be a folder that they automatically save to. When
> loading a previously saved file they should be listed in the app rather than
> opening the computer's file explorer."*

Round 1, item 15; recorded as **F87** (Impact High · Effort M · Risk Low, P13).
Chosen next because it is the smallest of the five remaining items, the tester
named it as the most annoying, and the precedent already exists in the codebase.

Branch: **V2.39**.

---

## What is actually there now (measured)

| | |
|---|---|
| `File → Save` with no path | `QFileDialog.getSaveFileName` — the OS dialog, starting in `""` (wherever the OS last was) |
| `File → Open` | `QFileDialog.getOpenFileName`, same |
| Where designs land | **Nowhere in particular.** Whatever folder the dialog happened to open in |
| The autosave | `~/.site-and-pattern_autosave.perma.geojson` — **a hidden dotfile in the home directory** |
| The one no-dialog path | `onboarding_flow.open_example` — builds the worked example, writes it to `user_data_dir()`, opens it through `MainWindow._load_from_path`. **Exactly the shape this feature needs**, already proven |

So the pieces are: a folder, per-save metadata, a browser, and moving the
autosave somewhere a person would look.

## The design

### 1 · A saves folder

`user_data_dir()/saves/`, beside the database. Created on demand. The platform
paths already exist and are already the single source of truth
(`src/user_paths.py`) — this is one more directory under them, not a new
concept.

A design saved with no path gets a filename derived from its `project_name`,
slugified, de-duplicated with a numeric suffix rather than overwritten. **Save
stops asking.** `Save As…` keeps the OS dialog for anyone who wants their
designs somewhere specific — this adds a default, it does not take away the
choice.

### 2 · The list, with enough to recognise a design by

Reading each file is the only honest way to describe it — nothing else knows
how many plants a save holds. Files are small (a 300-plant design is ~200 KB)
and the list is short, but the read is cached on `(path, mtime, size)` so
reopening the browser is free.

Per save: **name · when · plant count · species count · site**. That is what
tells one yard apart from another, and every one of them is already in the
project dict.

**No thumbnails, deliberately.** Rendering one needs the map widget, a live
QWebEngineView and a screenshot round-trip per save — a large amount of
machinery for a picture, and the wrong first move. If the counts turn out not
to be enough to tell saves apart, a thumbnail is the follow-on; promising one
up front would be the tail wagging the dog.

### 3 · The browser

A dialog listing the saves folder, newest first, with Open / Delete / Reveal in
folder, and a "Browse…" escape hatch to the OS dialog for a file kept
elsewhere. `File → Open` opens **this**; the OS dialog becomes the second
option rather than the only one.

Opening goes through `MainWindow._load_from_path` — the same code path as
today's File → Open and as the worked example. A second, near-identical load
path is how the panels and the title bar drift out of step, and the example
already proved the shared one works.

### 4 · The autosave moves

`~/.site-and-pattern_autosave.perma.geojson` → `user_data_dir()`. A hidden
dotfile in `$HOME` is nobody's mental model of where their work lives, and the
one moment it matters is the moment a user is most upset. **Migrate the old
path on first launch** — the same one-time move `user_paths.migrate_legacy_into`
already does for the data folder, and for the same reason: a person mid-recovery
must not lose the recovery file to a refactor.

## What could go wrong, and what is guarded

| Risk | Guard |
|---|---|
| A crash mid-save destroys the design | Already handled — `save_project` is atomic (temp + fsync + `os.replace`, `.bak` kept). This feature adds no new write path |
| The migration loses an autosave | Copy-then-verify-then-unlink, and a test that a legacy autosave is still offered after the move |
| Two designs called "Untitled" overwrite each other | De-duplicating filename, with a test |
| A corrupt file in `saves/` breaks the whole list | Per-file try/except; an unreadable save is listed as unreadable, not omitted and not fatal |
| Someone deletes the wrong design | Delete confirms, and `save_project`'s `.bak` survives |

## Deliberately not in this increment

- **Thumbnails** (above).
- **Cloud sync / sharing.** Not asked for.
- **A saves-folder preference.** `Save As…` already covers "somewhere else",
  and a setting for it before anyone has asked is a knob to maintain forever.
- **Renaming the file when `project_name` changes.** A file whose name moves
  under the user is worse than one that does not match a title.

## Verification

- `python -m unittest discover -s tests -t .` green.
- Qt-free core (`src/saves.py`) tested directly: slugify, de-duplicate,
  metadata read, corrupt-file tolerance, cache invalidation on mtime.
- The migration tested both ways: legacy file present, and absent.
- Hands-on: save a design with no path and find it in the list; open it from
  the list; confirm the title bar and panels match a File → Open.
