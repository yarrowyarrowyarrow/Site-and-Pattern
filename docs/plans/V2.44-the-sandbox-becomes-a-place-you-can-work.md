# V2.44 — The sandbox becomes a place you can work

## Context

V2.43 split the app into Learn and Design and made the seven reference
landscapes editable. Walking one immediately exposed four things it does not do,
all reported by the author:

1. **The walk controls don't match the 3D preview.** The reference window forces
   walk mode on with no way out, and has no time controls at all.
2. **Nothing is animated.** Planting, pulling and catching all happen instantly.
3. **A new plant appears full-grown**, identical to everything around it. It
   should start young — and *not* from seed: nursery stock is roughly **3 years
   for shrubs, 5 for trees**, because nobody plants those from seed.
4. **No split-screen 2D + 3D**, so a design can only be edited one way at a time.

Plus: *"there were also several other features I mentioned that have not been
implemented yet, you only mention the flight patterns but there was more."* That
is fair — the V2.43 hand-back surfaced section A of a six-section backlog. The
whole reviewed list is at the bottom of this document.

---

## What I found

### Walk mode is already identical; the *chrome* around it is not

`html/scene3d/08-modes.js` owns walk mode entirely, and both windows load the
same viewer — so WASD, drag-to-look, collision and the follow camera are already
the same in both. The difference is the Qt toolbar:

| | 3D Preview (`scene3d_window.py`) | Reference window |
|---|---|---|
| Year / month / hour | ✅ three sliders | ❌ none |
| Detail (Stylised/Balanced/Lifelike) | ✅ | ❌ |
| Reset view · Identify · Flyover | ✅ | ❌ |
| Leave walk mode | ✅ toggle button | ❌ **forced on, no way out** |

So this is not a controls problem, it is a **duplicated-toolbar problem**: two
windows hand-rolling bars over one viewer. The fix is to extract the bar once.

### There is no per-plant age anywhere — and year 0 means *mature*

`src/scene3d.py:growth_scale_factor(year, ytm, curve)` is the single source of
truth for "how big is this plant at year N", shared by the 2D timeline and the
3D scene so they cannot drift. Nothing carries a planting date: `_OPTIONAL_FIELDS`
in `src/project_store.py` is five keys, none of them temporal.

The trap: **year 0 currently returns factor 1.0** — it is the "mature design
reference", and year 1 shows everything *small*. Redefining that would change how
every saved design renders.

**The resolution, and it needs no toggle:** age is opt-in per plant. A plant with
no `planted_year` behaves exactly as today, so **every existing design is
untouched**. A plant that carries one is drawn at its own effective age. New
plants get one; the curated reference communities deliberately do not, because
they are meant to read as an established community.

Real maturity data, which decides whether the nursery ages actually show:

| Type | Typical `years_to_maturity` | Nursery age | Size at planting |
|---|---|---|---|
| Tree | 15–25 (default 15) | **5** | ~25–33% — a whip, clearly new |
| Shrub | 3–6, mostly 5 (default 5) | **3** | ~60% — a #2-pot serviceberry, which is honest |
| Herb / grass | 1–3 | **0** | plugs and seed, as today |

The ytm=3 shrubs come out fully grown at planting. That is horticulturally
*correct* — a three-year-old red-osier dogwood is a full-size shrub — so the plan
keeps the literal ages rather than fudging a factor to force visible growth.

### Animations collide with the full scene rebuild

The render loop (`08-modes.js:319`, `renderer.setAnimationLoop`) already has the
right shape: step functions (`animateWildlife`, `stepSpotlight`, `stepThreads`,
`updatePrecip`) called per frame. There is no generic tween registry, which is
the small missing piece.

The real obstacle is that **every edit currently rebuilds the whole scene** —
`_render()` → `build_scene` → `permaSetScene` → `disposeDesignGroup` — so any
animation is destroyed the instant it starts. Two ways out; the cheap one is
right: **play the animation first, rebuild after it lands.** Plants live in
`InstancedMesh`es whose `userData.pickId` maps instance → plant id (that is how
`scenePick` works), so a single instance's matrix can be scaled without touching
its neighbours. That is enough for all three animations.

### Split-screen has a home already

`src/app.py:283` builds a `QSplitter` with the map on the left and the side tabs
on the right. A second pane in the left column is a small structural change, and
both views already read one `_project`: `persistence.render_project_to_map()`
redraws the map, `build_scene` + `apply_scene` redraws the 3D.

## What ships

### 1. One 3D toolbar, used by both windows

New **`src/scene3d_toolbar.py`**: a `Scene3DToolBar(QWidget)` built from a
declarative spec, emitting Qt signals (`year_changed`, `walk_toggled`,
`detail_changed`, …). `Scene3DWindow` keeps every control it has today; the
reference window gets the subset that makes sense in a sandbox — **time (year /
month / hour), detail, reset view, identify, and a walk toggle that can be turned
off.**

This also lets the Learn side be genuinely simpler without a second
implementation: the same bar, told which groups to show. `scene3d_window.py` is
**868 lines** and should shrink; the reference window is **420/450** and must,
which is what makes the extraction the right shape rather than a nicety.

### 2. Per-plant age and nursery stock

- **`planted_year` joins `_OPTIONAL_FIELDS`** (`src/project_store.py`), so it
  round-trips through the GeoJSON feature with no schema change — it is project
  data, not catalogue data.
- **New in `src/scene3d.py`** (the shared model, so 2D and 3D cannot drift):

  ```python
  NURSERY_AGE_YEARS = {"tree": 5, "shrub": 3}      # everything else 0

  def effective_age(plant, scene_year, planted_year):
      """Age to draw this plant at. None planted_year = today's behaviour."""
      if planted_year is None:
          return scene_year            # unchanged: existing designs untouched
      return max(0, scene_year - planted_year) + nursery_age(plant)
  ```
- `plant_3d_state` and `placed_plants_3d_state` take the per-plant year and feed
  `growth_scale_factor` the effective age. `scene_contract.build_scene` passes it
  through from the feature.
- **`reference_edit.plant_at` and the map's placement path stamp `planted_year`**
  with the scene year at the moment of planting.
- The 2D map gets it for free — `map_js.py` already takes a `plant_id →
  maturity-factor` map, and it is computed from the same function.

**A new tree in a mature parkland now reads as a new tree**, which is the ask,
and it makes the year slider mean something in the sandbox for the first time.

### 3. Three animations, and the net

New **`html/scene3d/17-anim.js`** — a small tween registry (`addTween(ms, fn)`)
driven from the existing animation loop, plus the three:

- **Plant** — a soil puff at the point, and the new plant scales from 0 with a
  slight overshoot over ~500 ms. Because of (2) it is now scaling to a *nursery-
  sized* plant, so the two features reinforce each other.
- **Pull** — the instance tilts, lifts and shrinks over ~400 ms, with the
  consequence line appearing as it goes. The rebuild happens on completion.
- **Catch** — the net arc the backlog's item D described, over the existing
  `scenePick` raycast: a swipe, the critter shrinks toward the cursor, and its
  species page opens with `how='caught'` written to `discovered_species`. The
  ledger and the bridge for this shipped in V2.43; this is the mechanic on top.

`08-modes.js` is **372/600** and gains one `stepTweens(t)` line.

### 4. Split-screen 2D + 3D in Design mode

View → **Split view (map + 3D)**, or `Ctrl+Shift+3`. The left column of the
existing splitter becomes a vertical `QSplitter`: map above, `Map3DWidget` below.

- **New `src/controllers/split_view.py`** — the controller shim, so this costs
  MainWindow no methods (it is at **126/140**).
- Sync is one function each way, both of which exist: an edit on the map triggers
  a scene rebuild; an edit in 3D goes through the V2.43 bridge into
  `ProjectStore` and triggers `render_project_to_map()`. **Debounced**, because a
  drag on the map would otherwise rebuild the 3D scene per mouse-move.
- **Learn mode does not get this**, deliberately — a second view is exactly the
  complexity the Learn door exists to remove. Revisit if the sandbox asks for it.

**Cost to name:** a second `QWebEngineView` in MainWindow is real memory and GPU.
It is constructed lazily on first toggle and destroyed when the split closes.

### A · Creature realism — the flight problem *(the biggest remaining)*
Birds *"glide as if along a zip line"*; butterflies should go *"fast, fast, slow"*.
Diagnosed in full: `flapWings` is fed hardcoded constants that are not Hz, and
the body path is an exponential lerp **decoupled from the wings** — that
decoupling *is* the zipline. Three layers: beat frequency from morphology, bout
structure (burst + pause), and coupling the body to the wings so the bounding dip
and glide sink come from flight state.
**Blocked on data I want you to verify, not estimate:** birds have no attributes
table at all (24 species). Also: Pennycuick's formula gives ~13 Hz for a chickadee
against a measured 25–30, so it needs measured anchors and honest bands (P9). And
above ~40 Hz a wingbeat cannot be rendered at 60 fps — it must become a blur arc.

### B · Undo in the sandbox, and the graduation path *(new — I'd do this next)*
Two gaps V2.43 left that I did not flag loudly enough:
- **The sandbox has no undo at all.** Design mode has full undo/redo; a learning
  space where a misclick is permanent is the wrong way round.
- **There is no bridge between the doors.** "Take this landscape into Design" —
  turn the fen you built into a real design at your address — is the thing that
  makes Learn lead somewhere, and it is mostly a coordinate transform.

### C · Challenges and achievements
Briefs with win conditions over the sandbox — *"support 5 bee species on 20 m²"*,
*"keep something in bloom every week April→October"*. Scored by machinery that
already exists (`habitat_score`, `forage_calendar`, `habitat_nudges`). F13
(reference-community fidelity) is now effort S and is the natural win condition
for "rebuild the parkland from memory".
**Bank achievements for going outside** — the P11 counterweight, via F32/F33.

### D · The companion (F85)

*Do the cheap half first and separately:* ~12 of ~20 Site Info metrics have no

### E · The curriculum (F88) and plant ID (F83)

## What changed while building it

Five things the plan got wrong or under-specified. Recorded because a plan
nobody can learn from is worse than none.

1. **`src/reference_edit_flow.py` was not in the plan.** The toolbar and the
   net took `reference_ecosystem_window.py` to **515 of its 450-line ceiling**.
   That ceiling's own comment, written in V2.43, had named the seam in advance
   — *"the split is the edit half — the bridge slots and the trowel — into its
   own _flow"* — so the extraction was already designed. The guard working
   exactly as intended, for the second increment running.
2. **`Scene3DWindow` did not adopt the shared widget, and that is a deliberate
   partial.** Its `_year` / `_month` / `_hour` / `_detail` are read from a
   dozen places (`_when`, `_push_scene`, `_update_labels`, the flyover's month
   stepping); swapping them for `Scene3DToolBar` is a mechanical but wide
   change to a working 868-line file that this increment did not need. What it
   *does* now is import `MAX_YEAR` / `DETAIL_KEY` / `DETAIL_LABELS` from the
   shared module, so the numbers have one home, and
   `tests/test_viewer_controls.py` fails the build if the two windows stop
   offering the same viewer controls. **The guard is the anti-drift mechanism,
   not the extraction.** Say so rather than claiming a dedup that did not
   happen.
3. **A test caught a second `plant_3d_state` call** in `scene_contract.py` that
   the plan had not accounted for — the regeneration recruits. It turned out to
   be *already correct*: a self-seeded volunteer passes its own age
   (`int(rc["age"]) + 1`) and genuinely did come from seed, so it wants no
   nursery age. The test was made precise rather than blanket: what must never
   appear is a call passing the bare design `year` with no planting date.
4. **The catch releases the creature.** Not in the plan, and it should have
   been: a net that removes pollinators from a habitat is the wrong thing for a
   teaching tool to model (P11). It is caught, recorded, and put back.
5. **A test found a real abort hazard in the split view.** The debounce means a
   sync requested during a drag can fire *after* the user closed the split, by
   which point the viewer is a half-torn-down C++ object. An exception escaping
   a Qt slot calls `qFatal()` — a process abort with no traceback, surfacing in
   whatever ran next, which this app has been bitten by twice (V2.38, V2.40).
   `_rebuild_scene` now checks `qt_safety.is_alive` and wraps the push, and
   there is a test that closes the split and fires the timer anyway.
6. **`how='caught'` does not upgrade an earlier `'inspected'`.** V2.43's ledger
   keeps the *first* sighting's method, and a test pins that. Catching
   something you had already glimpsed therefore still reads as "inspected".
   Left alone deliberately — an achievement tier is the challenges increment's
   job, not a semantics change smuggled in here.

## Verification

**New tests:** `tests/test_plant_age.py` (nursery ages, effective age, and the
one that matters — *a plant with no `planted_year` renders exactly as before*),
`tests/test_scene3d_toolbar.py`, extend `tests/test_learn_mode.py` for the
animation/net contract and `tests/test_architecture_guard.py` for three new
ceilings.

```bash
QT_QPA_PLATFORM=offscreen QTWEBENGINE_CHROMIUM_FLAGS=--no-sandbox \
  python -m unittest discover -s tests -t .
```

The `-t .` is load-bearing. Install `PyQt6 PyQt6-WebEngine` + `libegl1` and the
scientific deps first — this is widget-heavy work and a green suite full of skips
proves nothing. Read `Ran N tests … OK`, not the exit code. `test_undo_redo`
segfaults in a GPU-less container; check it against a stashed tree before
believing it.

**Headless probe** — the backwards-compatibility property, which is the thing
most likely to go wrong:

```bash
python3 -c "
from src.scene3d import plant_3d_state, effective_age
p = {'plant_type':'tree','years_to_maturity':20,'mature_height_meters':8}
print('no planted_year (must equal today):', plant_3d_state(p,51,-114,10)['height_m'])
print('planted at year 10, viewed at 10  :', effective_age(p, 10, 10), 'yrs → nursery whip')
print('planted at year 10, viewed at 25  :', effective_age(p, 10, 25), 'yrs')"
```

### What the run actually said

**2,597 tests, OK, 10 skipped**, with PyQt6, PyQt6-WebEngine, the Qt runtime
libs and the scientific deps all installed — an increment this widget-heavy
proves nothing behind a suite full of skips. The remaining 10 are `bpy`
(Blender), a root-permissions case, and one import-order guard. Zero Qt or
WebEngine skips.

The first full run found one failure, and it was a good one:
`test_the_app_offers_the_style_by_name` asserted the literal text
`_DETAIL_LABELS = [...]` inside `scene3d_window.py`, which moving the constant
to the shared toolbar broke. The test's intent — *"'Low' told the user it was
worse. It is a choice."* — still held, so it now asserts the **value**, and
additionally that the window gets it from the shared module rather than
re-declaring a copy. A stronger test than the one it replaced, and exactly the
kind of breakage a text-level guard is supposed to produce when code moves.

`tests/test_undo_redo.py` is excluded from that count and still segfaults
mid-run in this GPU-less container, exactly as the CLAUDE.md runbook describes
and as V2.43 verified against a stashed tree.

**What I could not verify here:** the animations and the walk controls need a
real desktop with a GPU — nobody has watched a plant grow in, a shrub tilt out
of the ground, or a net swing. Those have text-level contract tests (the chunk
is loaded and stepped; the bridge call is the animation's completion callback;
every path still performs the edit) but the frames themselves have never been
drawn.

The split view is the exception and deliberately so: its layout surgery is
tested for real against a stubbed viewer, because taking the map out of its
column and putting it back is the one piece of this increment with genuine bugs
available — and a wrong order there leaves a working app with no map in it.
