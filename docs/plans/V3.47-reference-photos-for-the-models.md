# V3.47 · Reference photographs beside each plant's model

**The owner:** continue improving the 3D plant models, with more than one photograph of each
plant to work from (the V3.35 photo search they ran on their PC), focused on the plants native
around Edmonton.

This increment builds no model. It sets up what the model work reads: for each of the region's
250 reviewed natives, one sheet with the plant's model drawn by the app's real viewer beside its
reference photographs. The model work itself is the next increment, on its own branch.

## What was found

- **The earlier model work** is in [`docs/SPRITE_AUDIT.md`](../SPRITE_AUDIT.md) (three passes,
  V2.29–V2.33), [`docs/3D_SPRITES.md`](../3D_SPRITES.md), [`docs/3D_ASSETS.md`](../3D_ASSETS.md)

  own shape, F178), V2.93 (succulents), V2.94/V2.96 (leaf light, shrub shade). 3D_SPRITES.md
  says it plainly: *"The shapes against photographs. They follow the species' standard
  descriptions; no reference images were compared here."* The SPRITE_AUDIT compared against
  photographs of one exemplar per **archetype**, never per species.
- **The photo search** is `scripts/fetch_photo_candidates.py` (V3.35, F251). Run on the owner's
  PC, it writes `data/fetched/photo_candidates.json`: per plant, up to four research-grade
  photographs each in flower, leaves/whole plant, fruit and (woody plants) winter, three from the
  species' own iNaturalist page and the one the app has now, every one CC0, CC BY or CC BY-SA,
  with its credit, place and date. **That file never reached the repository**, and no picks were
  folded in: `data/plant_photos.json` holds two rows. It is not git-ignored, so it can simply be
  committed.
- **A session cannot reach iNaturalist's API, but it can reach the photographs.** Measured:
  `api.inaturalist.org` is refused by the proxy; `inaturalist-open-data.s3.amazonaws.com` answers
  200. So nothing but the candidate list (a few MB of JSON) has to come from the PC; the
  photographs (hundreds of MB) are fetched in whichever session needs them, and never committed.
- **Rendering one plant headless works through `html/yard_probe.html`'s shots mode**, the same
  path `scripts/render_yard.py` uses (Chromium's virtual-time budget, pictures read back from the
  DOM). The sprite gallery page itself never finished loading under headless Chromium; the probe
  does, about 13 s for four pictures. The scenes are the gallery's own
  (`html/sprite_gallery_scenes.json`, `species_<slug>`), built by the real `build_scene`.
- 249 of the 250 natives have a gallery scene. The missing one is *Crataegus chrysocarpa*: the
  scenes file is older than its row. `scripts/make_gallery_scene.py` rebuilds it.

## What was built

`scripts/model_references.py`, four steps, everything to `data/fetched/model_refs/` (ignored):

| step | does | needs |
|---|---|---|
| `status` | how many of the plants the candidates file holds, and which have no scene | nothing |
| `fetch` | downloads each plant's photographs at 500 px, writes `manifest.json` with credits | the open-data store |
| `render` | the model from the side at eye level and from above at 45°, July, fully grown | Chromium (in the container) |
| `sheets` | one JPEG a plant (model + numbered, labelled photographs) and `INDEX.md` by model group | Pillow |

`all` runs the last three. `--only NAME…` takes scientific or common names; `--all-plants` the
whole catalogue. Without the candidates file it falls back to the catalogue's own photographs
(usually one a plant) and says so on every line, so it is usable today and better tomorrow.

`tests/test_model_references.py` holds the plant selection, the candidates-first order and the
fallback, and the camera framing, offline.

### Decided

- **The photographs stay out of git.** About 250 plants × up to 19 photographs × ~100 KB is a
  few hundred MB, re-fetched in five minutes from the committed list.
- **The licence bar is the shipping one** (CC0, CC BY, CC BY-SA), because the candidates file
  already applies it, though these are references, not app content. Nothing here publishes them.
- **The sheet is the unit**, not loose photographs, so a model can be judged against twenty
  pictures in one read, and the model's picture is always the current viewer's.

## Handover: the model work (for the next session)

1. Read this, then [`SPRITE_AUDIT.md`](../SPRITE_AUDIT.md) (what was already fixed and the
   lessons: leaf cards once 13–15× life size, unnoticed by every gate), and the scene-3d skill.
2. `python scripts/model_references.py status`. If the candidates file is missing, ask the owner
   to commit it (instructions in the reply that set this up, and below).
3. `python scripts/model_references.py all` (about 15 minutes for 250 plants), then read the
   sheets by group from `data/fetched/model_refs/INDEX.md`. Score each against the audit's
   question: *would someone who knows this plant recognise it, and tell it from its neighbours?*
4. Fix by archetype where many plants share a fault, by species data (the morphology columns,
   `scripts/tune_morphology.py`) where one plant is wrong. After a viewer change re-run `render`
   and `sheets` for the plants touched (`--only`) and keep before/after sheets for the owner.
5. Keep the guardrails of [V3.43](V3.43-the-3d-preview-reviewed.md) (triangle budgets, the
   leaf-light hooks, the vertex-colour flag), the D2 decision (a site model: true shapes, sizes,
   colours, plain materials; photo textures only after 3D-6), and P12: the photographs are for
   form and colour only, never for anything about a plant's uses.

### Getting the candidate list from the PC

On the PC that ran `fetch_photo_candidates.py`, in the repository's folder:

```bash
git fetch origin refs/heads/V3.47:refs/remotes/origin/V3.47
git switch V3.47
git add data/fetched/photo_candidates.json
git commit -m "The photo candidates, for the model references"
git push -u origin HEAD
```

`git switch` refuses if the PC has uncommitted changes to tracked files; `git stash` first keeps
them. A `photo_picks.json` saved from the picking page is separate: send it to a session to fold
into the app with `scripts/fold_photo_picks.py`.
