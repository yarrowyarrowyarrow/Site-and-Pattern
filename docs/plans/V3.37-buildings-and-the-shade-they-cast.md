# V3.37 · Buildings that come, and the shade they cast

*The owner, with a screenshot of Site › Features: "I need a review of the
building outlines scan and import function. It doesn't seem to be working for
me and this is crucial for the Sun & Shade tab. I also think Existing Features
(or the 'Features' tab as it currently exists) should be accessible within Sun
& Shade. As a collapsible (initially collapsed) drop down that allows you to
pick the features that the sun path shade will then reflect."*

## What the screenshot says

- The status line reads *"OpenStreetMap didn't answer (busy or offline) —
  nothing was imported. Wait ~30 s and try again."*, the words
  `osm_features.import_osm_result` gave a fetch that failed: every Overpass
  server asked, and every one failed. The highlighted button is *Import Building
  Outlines*.
- *"Casting shade: 0 buildings · 4 trees"*: the tree half of a scan worked (four
  "Tree (detected)" on the map); the building half did not.
- So the computer reaches the internet. Whether Python's own connections do is
  less sure than it looks: after its first run the canopy-height map is read
  through GDAL's downloader, which keeps its own certificates.

**What could not be verified here.** This session's network refuses every
Overpass server (`overpass-api.de`, `overpass.kumi.systems`,
`overpass.private.coffee`), so the cause on the owner's computer is not known,
and the code as it was could not have said: see finding 1. Every candidate cause
is now either handled or named, and the real network code was run against local
servers that answer 429, an HTML page, a query cut short, nothing in time, a
self-signed certificate, and nothing at all.

## The review

The path: *Scan this area* or *Import Building Outlines* → `OSMWorker` →
`fetch_existing_features` → `_fetch_overpass` (the main server, the main server
again after 2 s, then one mirror) → `import_osm_result` → `canopy_footprint`
polygons → `shade.casters_from_project`. Parsing, the boundary filter and the
import were sound and tested. What was wrong, in the order it matters:

1. **The reason was thrown away.** `_post_overpass` returned `None` for every
   exception: a 429, a 504, a timeout, a certificate the computer could not
   check, a refused connection, an HTML error page. Nothing was logged, against
   `src/log.py`'s house rule. The status line said "busy or offline" whatever
   happened, and the log (`<data folder>/logs/app.log`) said nothing. That is
   why this review cannot say which it was, and why no later one could either.
2. **A busy main server was asked again after two seconds,** before the mirror.
   The main instance limits each address, and two seconds mostly got the same
   429 back, at the cost of 25 s each time it hung.
3. **One mirror.** With `overpass.kumi.systems` down or slow, nothing else was
   asked.
4. **No second opinion on a certificate.** On Windows, Python reads only the
   root certificates already in the computer's store, and Windows fills that
   store on demand, as a browser or a Windows program first needs each root;
   `ssl_bootstrap` steps in only when the store is empty. A server whose root
   nothing on the computer has needed yet fails in Python while the browser
   opens it. certifi ships in both installers and was never asked.
5. **A query the server cut short counted as an answer.** Overpass answers 200
   with `"remark": "runtime error: Query timed out…"` and whatever it had; read
   as complete, that is "Found 0 buildings" again.
6. **A yard's query declared a city's memory.** Overpass admits a query only
   while what it declares fits what the server has free; the default `maxsize`
   is 512 MiB, for a few hundred metres of buildings.
7. **Scan this area called a failed building fetch "0 buildings".** With the
   trees in and the buildings failed, the line read "found 0 buildings and 4
   trees", a yard with no buildings: the "Found 0" lie V2.13 took out of the
   import, back in the scan's summary.
8. **A second press started a second scan:** two more queries at a server that
   limits each address.
9. **The bulk download** (*Download buildings for this area*) fetched every
   street in each of its fifteen 3 × 2 km parts as well (`fetch_buildings` left
   `roads` at its default), a heavier query for a busy server to turn away; and
   a run on which nothing answered said *"Building pack ready — 0
   footprints"* and marked the pack complete. An empty pack falls through to the
   live import, so that one only lied; a pack with some parts missing could
   answer for a yard on the seam and skip the live fetch.
10. **A shade map on screen did not take in an import or a scan.** Drawing or
    editing a shape redrew it (`_refresh_shade_if_active`); importing did not.

## What changed in the fetch

- **Each failure is kept** as an `Unanswered(host, kind, detail)`: *busy* (429,
  502–504, or a query cut short), *slow*, *refused* (any other HTTP status; a
  403 would be a block), *certificate*, *garbled* (not Overpass's JSON),
  *unreachable*. Each is logged, routine kinds at INFO and the rest at WARNING,
  and *"no server answered (…)"* names them all. `failure_words` makes the one
  sentence the status line shows, worst news first, always beginning
  *"OpenStreetMap didn't answer"* so a failure never reads as an empty answer:
  *"OpenStreetMap didn't answer: its servers are busy, so nothing was imported.
  Try again in a minute."*
- **The order:** the main server, then `overpass.private.coffee` (new, credited
  in `src/services.py`), then `overpass.kumi.systems`; the main one again, after
  five seconds, only when it said it was busy.
- **A certificate the computer cannot check is checked against certifi's list**
  before it counts as a failure, and that list is used from then on in the
  session, with a warning in the log. Still a checked certificate; asked only
  after the computer's own list said no, so antivirus or a work network that
  installs its own root keeps working.
- **While it moves between servers the status line says so**: *"Still asking
  OpenStreetMap: overpass-api.de is busy, so another server is being tried…"*.
  A slow server costs 30 s and four of them two minutes, which reads as hung
  unless something says otherwise (`OSMWorker.progress`).
- A *runtime error* remark is *busy*, and the next server is asked.
- A box under about 1 km a side declares `[maxsize:]` 64 MiB. The client waits
  30 s for the server's 25.
- `import_osm_result` and the scan's summary say why; the scan's summary says
  how many trees came and that no buildings did. One scan at a time.
- **The bulk download** asks for buildings only, asks a failed part once more at
  the end, and when one still fails says how many and why and does not mark the
  pack ready (`DownloadFailed`).
- A shade map on screen follows a scan, an import, a tree detection and a scan's
  review taking finds out.

If buildings still do not come after this, the status line names the kind, and
the log names each server and what it said. The next step after that would be a
second source of building outlines that is not Overpass (open footprints, the
V3.09 plan's T6), which is a bigger change and a new service, so not taken here.

## Existing features in Sun & Shade (F252)

**Where it went.** The owner kept Site › Features in the surface audit
(`site-features: keep`, with the scan rework that V3.10 did), and drawing a
building by hand is data entry, as V2.38 argued when it moved the shade map out
of that page. So the Features page stays, and Sun & Shade gains **Existing
features ▸**, closed when the app opens, inside *Cast shade* under the line that
counts what casts: every tree and building already on the site, ticked while it
casts shade, with **Scan this area** and its status line beside them. Drawing or
marking one by hand opens Site › Features (with Advanced tools on, as those
tools are there). This reverses half of V2.38's call ("the existing-features
import stayed on the Site tab"), at the owner's ask; `analysis_panel` says so.

**One rule, everywhere the shade is computed.** An unticked feature carries
`shade_off: true` and `shade.casters_from_project` leaves it out, so the shade
map, the planting zones, Plan My Yard and the over-time model all agree.
Absent means it casts, and ticking it again removes the key, so a design that
never switched anything off is the file it always was. An optional property on
an existing type, so the file format's version does not change.

**What it does not change, on purpose.** The feature stays in the design: drawn,
kept out of by the planner (a building switched off is still not planted on),
and in the 3D preview with its own shadow, which three.js casts from the mesh.
The question the list answers is "what does my shade map count", not "what is
there". The 3D preview could follow if the owner wants it to.

**The rows.** Buildings first, then trees, nearest the yard's middle first:
*"Building (OSM) · 6 m tall · 22 m south"*, *"Tree (detected) · crown 6 m ·
11 m tall · 11 m north-west"*. The distance and direction from the middle of the
yard (the outline's middle, else the pin) are how four "Tree (detected)" rows
are told apart; picking a row frames its feature on the map, as the scan's
review does. The header counts: *Existing features (3 of 4 cast shade) ▸*, and
the summary above it says *"1 switched off below."* (on Site › Features, *"in
Sun & Shade"*).

**Undo.** A tick is one undo step, *Tick all* and *Untick all* one each. The
list holds a tick the moment it is made, so the refresh the change brings finds
nothing moved and the shade is asked for once; an undo, a redo or a file opened
moves a tick under the list, which notices and asks a shade map on screen to
follow. (A snapshot holds the shade map as it was when the step ended, before
the recompute finished; the recompute is what corrects it, here and for every
other edit that redraws the shade.)

`src/shade_features.py` is the section, `src/shade_features_flow.py` connects
it, and the rows and the switch are Qt-free in `src/sun_shade.py`, which also
took the review list's row words from `features_scan_flow` so the two lists
read alike.
