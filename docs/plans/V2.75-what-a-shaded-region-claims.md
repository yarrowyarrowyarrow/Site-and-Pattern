# V2.75 — the review from a botanist

## Context

An outside reviewer with botanical expertise read grownativeplants.ca and sent
eight criticisms. Every one was checked against the code. **Six are hits, two
have a wrong premise with a right point underneath, and three faults were found
that the review only gestured at.** The unifying diagnosis is one this repo
already has a name for: *an unmarked estimate is safe exactly until something
starts asking it questions* (P9, `DATA_GAPS.md`). The site began asserting
nativity, range and colour to strangers, and a stranger who knows the flora read
them as assertions.

**No names appear in this plan or in anything it produces.** The feedback is
recorded by its content. `docs/USER_FEEDBACK.md`'s convention is to quote
verbatim, and that stands — quotes go in unaltered, attributed to *an outside
reviewer*, with no name for the reviewer and none for the author.

The most serious findings are not the ones they listed.

**1. Ranges are derived with a 5 km proximity buffer, not by containment.**
`src/ecoregion.py:139` sets `_NEAR_BOUNDARY_M = 5000.0`, so `lookup_ecoregions`
returns every ecoregion whose boundary passes within 5 km. That buffer was
written in V2.67 for *site detection* — "which ecoregion is my yard in", where a
±900 m outline makes a near-boundary yard genuinely ambiguous.
`ranges_for_species` defaults its `lookup` to that same function
(`src/ecoregion_ranges.py:80-81`) and inherited it silently. Measured over 4,000
random points inside the layer: **16.4% are credited to two or more ecoregions**
(640 to two, 17 to three). The shipped counts in `data/plant_ecoregions.json`
were derived with it active — the buffer commit (2026-08-18 05:54) precedes the
re-derivation commit (07:06). The module docstring at `:75-78` still describes
the pre-V2.67 behaviour, when the hand-traced polygons literally overlapped.
The review guessed this fault and named 900 m; the real figure is 5,000 m, and
their worked example is in our data — *Aster alpinus*, a montane species,
carries 72 Aspen Parkland records.

**2. The nativity generator is frozen against a vocabulary that no longer
exists.** `scripts/tag_prairie_provenance.py` writes `native_provinces`, which
is what the site publishes as "Native to". Its docstring is candid that SK
status is *"inferred from ecoregion continuity, not a per-species range map"* —
but its `_SK_SHARED` set (`:33-36`) holds the **pre-V2.38 key names**, and
V2.72/V2.73 replaced the vocabulary underneath it. Simulated re-run:

```
shipped ab_ecoregion tokens:  zone_prairies 303 · mixed_grassland 123 · wet_meadow 81 · riparian 80
_SK_SHARED intersection:      riparian, wet_meadow   (2 of 6 keys still exist)
currently tagged SK:          356
would be tagged SK today:     119        →  237 species would change answer
```

So the site's nativity claim for **237 of 431 species** is the output of a
heuristic that would no longer produce it. It is not a coarse inference; it is a
stale artefact, and nothing could have said so.

**3. The data gate is 70% noise and hides this.** `validate_all()` returns 0
errors and 430 warnings — **303 of them are `unknown ecoregion key
'zone_prairies'`**, because `validate_plant` (`src/data_quality.py:490-497`)
checks tags against the 24 bare ecoregion keys and does not know the tree's
prefixed `zone_*`/`sub_*` keys that V2.73's own migration wrote. The gate has
been calling the migration's output invalid on 303 species, and the volume
buries everything else.

**And the example that settles the argument:** two published species pages are
both titled *Stiff Goldenrod*. `Solidago rigida` says native to AB and SK;
`Oligoneuron rigidum` says `native_to_alberta = 0`, native to SK and MB. Same
taxon. Known since V2.69, left alone as "a data decision", and there is no check
that could fail on it.

Decisions taken with the owner: honesty pass **plus** fetch machinery this
increment; narrow honestly to AB/SK; remove *Helianthus giganteus* now and hold
the Old World name cases for the authority pass; no reply drafted; **and plot
the actual observation locations**, which the review is right is the thing that
would resolve most of the uncertainty it raises.

## F136 · Containment, not proximity — and cache the points

**The fix is a parameter, not a new default.** `_NEAR_BOUNDARY_M` is correct for
site detection and was reasoned about in V2.67 (`src/ecoregion.py:126-138`);
changing it globally would break the thing it was written for. Add `near_m` to
`lookup_ecoregions`, defaulting to `_NEAR_BOUNDARY_M` so every existing caller
is unmoved, and have `ranges_for_species` pass `near_m=0.0`. Rewrite the stale
docstring at `ecoregion_ranges.py:75-78`, which still describes overlapping
hand-traced polygons.

**The data cannot be re-derived here, and that is the real lesson.** Only counts
were ever kept, never the points, so a change to the geometry, the buffer or the
threshold costs a full re-fetch of ~400,000 GBIF records — and a *point map* is
impossible without them. Change `scripts/seed_ecoregion_ranges.py` to write what
it fetches to `data/fetched/plant_occurrences.json`:

| field | why it is kept |
|---|---|
| `decimalLatitude` / `decimalLongitude` | the point; 4 dp (~11 m), matching the polygon file |
| `coordinateUncertaintyInMeters` | **the direct answer to the boundary objection** — a record uncertain to 20 km cannot support an ecoregion assignment at all |
| `year` | currency per record, not just per fetch; lets a 1908 sheet and a 2024 photo be told apart |
| `basisOfRecord` | herbarium sheet vs human observation |
| `datasetKey` | which source; how iNaturalist records are identified (F139) |

`data/fetched/` already commits multi-MB fauna caches (3.7 MB and 9.5 MB); if
this exceeds ~30 MB, gzip it rather than dropping fields — the fields are what
make it re-usable.

**Also fold in, while the seeder is open:**
- **The spatial join runs against the simplified polygons.**
  `tools/ecoregions/export.py:48-96` simplifies to 0.008° (~900 m) and rounds to
  4 dp *before* `adopt.py:167` writes `data/ecoregions_canada.geojson`, and that
  is the file `lookup_ecoregions` ray-casts against. Stage 4 (`validate.py`)
  runs on the unsimplified GeoPackage and never sees the shipped file. Ship the
  full-resolution polygons for the join and keep the simplified ones for
  display — the file is 900 KB simplified, and the join is the one place the
  precision matters.
- **Coordinate uncertainty as a filter.** With the field cached, drop or flag
  records whose uncertainty exceeds the distance to the nearest ecoregion
  boundary. This is a better instrument than any threshold on counts, and it
  answers the objection at its own level.
- **Quality grade.** Currently only `hasCoordinate`,
  `hasGeospatialIssue=false` and three excluded `basisOfRecord` values. Decide
  explicitly whether to add `identificationVerificationStatus`; if not, say so
  on the Method page. The question about correct identification deserves a
  stated answer either way.

**Handover.** After the re-fetch, the buffer, the floor and the uncertainty
filter all become offline knobs, and the diff between the old and new
`plant_ecoregions.json` is the honest measure of what the buffer cost. Report
that number.

**Files:** `src/ecoregion.py`, `src/ecoregion_ranges.py`,
`scripts/seed_ecoregion_ranges.py`, `tools/ecoregions/export.py`,
`tests/test_ecoregion_ranges.py` (a boundary-point case that fails today).

## F139 · Plot the observations

*"Listing # of observations in an ecoregion doesn't explain where they are in
it — scattered throughout? isolated outliers?"* That is the strongest question
in the review and the honest answer is a dot map. Depends on F136's point cache.

**`scripts/plot_occurrences.py` — the diagnostic, first and unconditionally.**
A dev tool, not a panel: per species, draw the cached points over the ecoregion
polygons, reusing `src/ecoregion_map.py`'s projection and
`src/ecoregion_basemap.py`'s ground so the dots land in the same coordinate
system the shading uses. Output inline SVG, no dependency, matching the house
style. Modes worth having:

- `--species "Aster alpinus"` — one species, the QA case
- `--buffer-artefacts` — points assigned to a region they are **not inside**,
  which draws the 5 km bug as a picture and measures what F136 recovers
- `--sheet` — a contact sheet over many species, the shape
  `scripts/colour_worklist.py` already established for the colour backlog
- colour dots by `datasetKey` provenance and scale them by
  `coordinateUncertaintyInMeters`, so an imprecise record looks imprecise

This alone is worth the increment: it is the instrument that would have shown
the montane-species-in-parkland problem years ago, and it needs no permission
from anyone because nothing is published.

**Publishing the dots is a separate decision with two real constraints, and
neither is a formality.**

1. **Licence.** `docs/DATA_SOURCES.md:222` currently rests the GBIF position on
   *"Only the derived counts are stored, never GBIF's records themselves … a
   number we computed, not a dataset we redistribute."* Publishing coordinates
   changes that sentence. GBIF records carry per-record licences; the map may
   only draw points whose licence permits it, and `DATA_SOURCES.md` must be
   rewritten to say what is now redistributed.
2. **Sensitive species — this one can cause harm.** iNaturalist obscures
   coordinates for rare, threatened and collectible taxa precisely so that
   publishing them does not lead a collector to the plant. Orchids and
   cacti in this catalogue are exactly that category. So: **never plot a point
   at finer precision than its source published it**, honour the obscured flag,
   and where a species is sensitive fall back to the region shade with a line
   saying why the points are withheld. Note the bitter irony worth recording —
   the rare species the review rightly says the 3-record floor under-serves are
   the same ones whose points must stay coarse.

**The cheap half that has neither problem**, and which the review explicitly
suggested: link out. A species page can carry *"see all observations"* pointing
at the GBIF and iNaturalist species pages, which shows the reader the live,
current, zoomable map without us republishing a single coordinate. It also
answers item 2's "the iNat database is live and changing" — the link is always
current where our snapshot is not. **Do this in F135 regardless of how the
publishing decision lands.**

**Recommended sequencing:** the diagnostic script and the outbound links ship
this increment; the published dot layer ships once the licence and sensitivity
review is written down, as its own backlog row. Do not let the second block
the first.

**Files:** `scripts/plot_occurrences.py` (new), `src/ecoregion_map.py` (a
point-layer helper, if it fits under the line ceiling — otherwise its own
module), `src/static_site_species.py` (the outbound links),
`docs/DATA_SOURCES.md`.

## F137 · Nativity and taxonomy from an authority

**Why VASCAN answers two questions at once.** One request per species to
`https://data.canadensys.net/vascan/api/0.1/search.json?q=<name>` returns the
matched taxon, its **accepted name**, its **synonyms**, and a `distribution`
array carrying `locationID` (`CA-AB`, `CA-SK`, `CA-MB`) with
`establishmentMeans` (native / introduced / ephemeral) per province. That is
per-province nativity *and* a taxonomic backbone — the two things the catalogue
has never had — in **431 requests**.

**`scripts/fetch_flora_nativity.py`**, modelled directly on
`scripts/fetch_fauna_nativity.py`: a `--probe` mode of three species first (that
mode is what settled two failed fetch designs in V2.59 and V2.61), the same
throttle and retry discipline as the ecoregion seeder, a `FetchFailed` that is
distinguishable from "no record" (the ecoregion seeder's first run recorded 208
rate-limited species as growing nowhere), and output to
`data/fetched/flora_nativity.json` keyed by the name we shipped, carrying:
accepted name, synonym flag, per-province `establishmentMeans`, and `unstated`
where VASCAN is silent. **`unstated` is the honest and expected answer for some
rows and must never collapse to a verdict.**

**`scripts/ingest_flora_nativity.py` — report by default.** It proposes; it does
not apply. This is the V2.59/V2.60/V2.61 pattern, and it earned its place three
times (23 false Monarch hosts, 62 wrongly binned bird edges, 20 orphaned
animals). Four output buckets: *confirmed* · *province narrowed* (the AB,SK → AB
case, expected to be the largest) · *not native here* (the *Rudbeckia* shape) ·
*name superseded*.

**What it must not do.** No automatic deletion — every removal goes through
`data/excluded_taxa.json` with an `authority` string, per V2.74. And the synonym
results are a **report**, not an auto-rename: merging `Solidago rigida` with
`Oligoneuron rigidum`, or deciding whether `Achillea millefolium` should be
`var. occidentalis` beside the `Achillea borealis` we already ship, changes
plant ids, `plant_fauna` keys and public URLs. That is its own increment.

**Retire `tag_prairie_provenance.py`, do not repair it.** Fixing `_SK_SHARED`'s
key names would re-bless the heuristic the review is right to reject and would
silently rewrite 237 species. Freeze its output, mark it superseded in the
docstring, and let F138's guard fail if anyone re-runs it against a drifted
vocabulary.

**Files:** `scripts/fetch_flora_nativity.py` (new),
`scripts/ingest_flora_nativity.py` (new), `scripts/tag_prairie_provenance.py`,
`docs/DATA_SOURCES.md` (a VASCAN row: API terms, attribution, that we store
derived per-province verdicts and not their dataset).

## F138 · The gate can fail on what it currently cannot see

**Un-break the ecoregion check first.** `src/data_quality.py:490-497` must
accept `zone_*` and `sub_*` keys via `src/ecoregion_tree.py`. This drops 303 of
430 warnings and is the precondition for anything else being visible.

**Three new checks:**

1. **Contradictory nativity for one taxon** — *error*. Two rows whose
   `scientific_name`s are known synonyms of each other, or which share a
   `common_name`, must not disagree on `native_to_alberta` /
   `native_provinces`. Fails today on *Stiff Goldenrod*, which is the point.
2. **A nativity claim with no evidence and no authority** — *warning*, naming
   the species. Ten published rows have no entry in `data/plant_ecoregions.json`
   at all: *Andropogon gerardii*, *Oenothera caespitosa*, *Elodea canadensis*,
   **Helianthus giganteus**, *Agoseris parviflora*, *Penstemon lyallii*,
   *Spiraea douglasii*, *Spiraea alba* var. *latifolia*, *Calamovilfa
   longifolia*, *Oligoneuron rigidum*. Occurrence is not nativity and this check
   must not imply otherwise — it flags *nothing anywhere agrees or disagrees
   with this row*, which is exactly how *Rudbeckia hirta* survived.
3. **Provenance-generator drift** — *error*. If
   `tag_prairie_provenance._SK_SHARED` names keys the shipped polygon file does
   not define, fail. This is the check that would have caught the whole of
   Context 2 the moment V2.72 landed.

**Helianthus giganteus comes out**, following V2.74's procedure exactly:
`data/excluded_taxa.json` entry with the authority (VASCAN records it native
from Ontario eastward; it is not in Moss, *Flora of Alberta*) and a
`disagreement` note that it had **zero** occurrence records rather than many;
then sweep its `plant_fauna_master.json` edges, check for newly orphaned fauna
against `curate_new_fauna.writable()` (V2.74 found six), check `polycultures.py`,
`onboarding.py` and the sprite gallery for design-element uses, and bump
`_SCHEMA_VERSION` 75 → 76.

**The Old World name cases are flagged, not fixed**, per the decision above.
Record in `docs/DATA_GAPS.md` with the evidence: `Achillea millefolium` shipped
beside its own segregate `Achillea borealis`, both claiming AB,SK;
`Fragaria vesca`, `Prunella vulgaris` and `Juniperus communis` shipped as bare
Eurasian binomials with no infraspecific rank; `Aster alpinus`;
`Deschampsia caespitosa` where FNA and POWO use `cespitosa`, so a lookup on the
accepted spelling misses. Note what the catalogue got *right* — the genus
segregations (Aster→Symphyotrichum, Polygonum→Persicaria, Zigadenus→Anticlea)
are done, and `Pulsatilla nuttalliana` is the correct NA name.

**Files:** `src/data_quality.py`, `data/excluded_taxa.json`,
`data/plants_master.json`, `data/plant_fauna_master.json`, `src/db/plants.py`
(schema bump + v76 note), `docs/DATA_GAPS.md`, `tests/test_data_quality.py`.

## What actually shipped, and where it differed from the plan

Written after the work. Four things went differently, and two of them were
caught by tests rather than by reasoning.

**The plan said "Ship the full-resolution polygons for the join". It did not
happen, and that was the right call.** `tools/ecoregions/export.py` simplifies
to ~900 m *before* `adopt.py` writes the file the join ray-casts against, and
stage 4's validation runs on the unsimplified GeoPackage and never sees the
shipped file. That diagnosis stands. But regenerating the full-resolution layer
needs the tools pipeline, which needs two sources with open egress and ~150 MB
of gitignored input — none of it reachable here. Adding untested code to a
pipeline that cannot be run is how `hrdem._rasterio_sampler` shipped unable to
open a local file. It is a backlog row with the exact diagnosis, and the
**coordinate-uncertainty filter** answers the same objection at a level that
*can* be tested offline: it acts per record, for a reason the record states
about itself.

**`static_site_species.py` hit 351 lines against a ceiling of 340**, and the
split was better than the ceiling forcing it. The seam was already named in
that module's own docstring — "a range map with its evidence" is one of the
species page's four parts, and it is the part the review spent most of its
words on. `src/static_site_range.py`.

**Two guard tests caught real regressions, both mine.**
`test_the_validator_refuses_an_empty_vocabulary` caught the gate fix defeating
its own safety property: widening the key set with a second source meant the
"refuse to validate against nothing" check could never fire, because the tree
walk supplied 51 keys even when the polygon file supplied none. The refusal now
happens *before* the widening. And `test_every_value_in_use_has_a_label` caught
that removing the Manitoba filter option was not enough — one row carries
`SK,MB`, so the extractor kept emitting an unlabelled `MB` value, which renders
as an empty checkbox. Clipped at the extractor, not in the data: that plant
really is native to Manitoba; what is untrue is that this catalogue can answer
questions about it.

**CLAUDE.md says em dashes are "guarded by a test" and no such test existed.**
`_esc` normalises them, so every string passing through it is safe — but a dash
written straight into an f-string template never meets `_esc`. This
increment's first draft of the range copy shipped an `&mdash;` in exactly that
position and the suite stayed green. Now guarded, both spellings, over every
rendered page.

**The full suite found two more, and both were guards rather than bugs.**
3,307 tests, two failures. The flower-colour snapshot went yellow 83 to 82,
which is *Helianthus giganteus* leaving with its yellow floret: the second
release running where that snapshot was the only thing in the suite that said
a catalogue row had gone. And two skill documents quoted
`_SCHEMA_VERSION = 75` against code saying 76 — the same guard that fired in
V2.74 for the same reason. Those files are read at the start of every session,
so a stale fact in one is a wrong instruction rather than a stale comment.

### What could not be verified here

The proxy answers 403 to `data.canadensys.net`, `api.gbif.org` and
`api.inaturalist.org`, so:

* **F137's fetchers have never spoken to VASCAN.** They ship tested against a
  fake transport, and deliberately with *no fixture asserting VASCAN's response
  shape* — V2.59 lost an afternoon to a fetch whose fixture encoded the same
  wrong guess as the code, so the parser accepts several spellings per field and
  `--probe` reports which ones the live API returns. **Run the probe first.**
* **The shipped occurrence counts still carry the 5 km buffer.** The derivation
  is fixed and the data is not; only a re-fetch corrects it. `/method/`
  discloses this as a known limit of the build rather than leaving a reader to
  find out.
* **`scripts/plot_occurrences.py` has never drawn a real harvest.** It is
  tested against a synthetic point set. A fixture cache written during
  development was deliberately deleted, and a test now fails if one reappears
  in `data/fetched/` — an invented file there is indistinguishable from a real
  one.

### The skips, named rather than counted

The suite reports 57 skips with PyQt6, PyQt6-WebEngine, rasterio and pyproj all
installed, and a skipped test proves nothing, so they are worth naming:
**shapely** and **Pillow** are absent and are pip-installable (they gate the
shade, wind-shadow, scan-import and photo-import modules — real code, and worth
installing before trusting a green run that touches geometry); **bpy** is
Blender's Python and is not reasonably installable here; the rest are
data-conditional (`no communities seeded`, `model assets not present in this
checkout`) rather than environmental. Nothing in this increment touches
geometry, photo import or Blender assets, so none of those skips masks a change
made here — but the next increment that does should install the first two
first.
