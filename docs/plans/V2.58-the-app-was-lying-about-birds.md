# V2.58 — the app was lying about birds

**Eight items of author feedback on V2.54–V2.57, tested together for the first
time.** *Design principle P9 — uncertainty is a feature; never false precision.*

## The report that mattered

> *"The screenshot list of plants has no animal interactions… I find this sus as
> these are all native and 16 plants… did something break. This is the biggest
> bug imo."*

Nothing had broken, and the instinct was still right — because the **app's own
output justified it**. That design of sixteen boreal understory natives scored
57/100 and reported:

    caterpillars: True, n_caterpillars: 1, birds: True, n_birds: 0,
    complete: True, status: "complete"

and the Analysis panel printed *"Food web — supports caterpillars and the birds
that eat them"* about a design the app held **zero bird records** for.

Two separate failures behind it, and only one is a data problem.

### 1. A false claim, and it is the V2.53 bug running backwards

``has_birds`` read ``n_birds > 0 or bool(bird_species)``, and ``bird_species`` is
the list of plants carrying the ``bird_food`` **tag**. So a tag with no record
behind it asserted the link and completed the web.

V2.53 fixed the case where the *tags deny* what the *edges document* — and its
own docstring described ``food_web`` as "edge-derived", which was never true.
The mirror case, where the tags **claim** what the edges do not record, was left
standing. The prose escaped because those lines were written defensively (each
checks the bool *and* the count); ``status`` and ``complete`` were not.

Fixed: the two sources are reported apart (``birds_evidence`` /
``caterpillars_evidence`` ∈ documented / tag_only / none), **"complete" now means
documented**, and a new ``unverified`` state carries its own wording. The
``food_web`` block is explicitly un-summed, so **no score moved**.

### 2. The coverage was invisible

``plant_fauna`` holds 361 edges over **99 of 437 species**. Fifteen of the
author's sixteen plants are among the other 338. The app never said so, so a
thin catalogue read as an empty ecology — or as a bug.

Every relevant surface now leads with it:

> Wildlife records exist for 1 of these 16 species. The other 15 are not
> recorded as supporting nothing — they are simply not recorded yet.

Genus-level inference was measured as a shortcut and **rejected**: it rescues 59
of 338 (23% → 36%) and would put inferred relationships in front of users to fix
a sourcing problem. Backlogged as **F125** — real cited edges from GBIF,
iNaturalist and HOSTS, which needs a session with egress.

## The road data

``osm_features`` already fetched trees and buildings from Overpass; it now
fetches ``highway`` ways too, and ``src/frontage.py`` turns those plus the
boundary into which edge faces the street. ``cues_to_care`` uses it, so the line
reads *"the east edge, from mapped road data (Maple Street)"* instead of
*"assuming the street is on the south side"*.

**The assumption is demoted, not deleted.** No road data, no network, or nothing
within 60 m and it falls back — and always says which it is, because a
measurement that cannot admit when it is guessing is worse than a guess that can.

Three things went wrong building it, all caught by probing rather than by
reasoning:

* **The first version named the wrong edge.** It took the nearer *endpoint* of
  the winning road segment rather than the closest *point* on it. A street runs
  well past the lot it serves, so both endpoints sit diagonally away — a due-east
  road reported as "south-east". Now it projects onto the segment.
* **`_ring_lnglat` silently ate roads.** It demands three distinct vertices and
  **closes** the ring, which is right for a building footprint and wrong twice
  over for a street: a two-node way is a real road segment, and closing the line
  invents a return segment to measure against. Roads get `_line_lnglat`.
* **Roads must not inflate the import count.** They are useful precisely because
  they are *outside* the property; counting them would pad "found 12 buildings"
  with things the user never asked to place.

## How it was verified

25 new tests. `test_food_web_evidence` pins that **"complete" means documented**
and that coverage is reported (including that a fully-recorded design is *not*
nagged about it). `test_frontage` checks a street on each of the four sides from
a road running past the lot — the case that caught the endpoint bug — plus the
fallbacks, the storage round-trip, the two-node parse, that footpaths are not
streets, and that roads do not inflate the import count.

Full suite: **2992 tests, OK, 98 skipped**, run in halves.

`html/map/03-plants.js` is now **at** its 950-line ceiling; the comment there
names the seam (`showPlantContextMenu`) for whoever adds the next item.

## What could not be verified here

No display, so nothing was clicked: the tooltip's *appearance*, the relocated
button, and the new map menu item are all reasoned and unit-tested rather than
seen. **No live Overpass call was made** — the road fetch is exercised against a
fixture response through the real parser, so the query string and the parsing are
tested but the network round-trip is not.
