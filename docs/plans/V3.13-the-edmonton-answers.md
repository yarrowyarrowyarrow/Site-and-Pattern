# V3.13 — the owner's Edmonton answers

The owner, after answering on the review page V3.12 published: *"I'm all done
my review you can continue."*

This is F220's data job (the BACKLOG row *The Edmonton review*), not a new
feature, so it takes no ID. It is its own release, as V3.12's plan said it
would be. The updater compares `(major, minor)` only, so a list that changes
on the V3.12 branch never reaches an install that already has V3.12.

`scripts/derive_local_flora.py --merge` checked them and wrote them:

## Found on the way: a non-native parent could still be placed

`filter_library` lists a top-level community whose *variation* passes, as the
heading over that variation (`{"self": False, "children": [...]}`). That is
right for a search, where the parent gives the match its context. Under
*Edmonton natives only*, though, the heading is a normal, selectable and
placeable row. A community with a plant not native here was therefore still
one click from the map, which is exactly what the owner asked not to see.
No V3.12 data could show it, because no variation passed while its parent
failed. The owner's answers made one do so: *Native Prairie Aromatics*, a
variation of *Aromatic Herb Circle*, whose parent keeps Self-heal (answered no)
and Sitka Valerian (no record within 50 km).

Fixed in two places:

- **`filter_library`.** Under `native_near`, a parent that fails is never
  listed. Each of its passing variations is listed in its own right, as
  `{"self": True, "children": []}`. Without the switch nothing moves.
- **The panel.** A passing parent no longer shows its non-native variations,
  which it did, because a passing parent showed all of them. The "N hidden"
  line now counts the parents it hid rather than subtracting row counts, which
  a promoted variation would have thrown off.

Both are checked in tests: a synthetic index pins the rule, and the existing
library test, which iterates every shown community, failed on this data
before the fix. The real panel was also driven offscreen. With the switch on,
it shows 22 rows and "47 hidden", with no row or variation carrying a plant
off the list.

## The offline generator

With *Edmonton natives only*, an Aspen Parkland yard's offline pick now leads
with **Pin Cherry Community**, followed by two Edmonton communities. The picker
scores +2 per goal hint ("Edmonton") and +3 for the site's region words
("aspen parkland", "prairies"), and Pin Cherry's description says "the native
cherry of the prairies". Every member passes the list, so the promise holds.
Raising the goal hint above the region would change every goal's pick, which
is a scoring decision for another increment. The test now asserts what matters:
nothing picked is foreign, and the Edmonton communities are among the picks.

## Tests that assumed nothing was answered

Four V3.12 tests read the shipped list as if every borderline species were
unsettled: Pin Cherry's page saying "Not settled", the website's waiting fold,
the data gate's "ruling not derived" check (its example ruling now matched the
list), and the generator's pick. They now set up their own state.
`_unreviewed()` strips the answers off named species in a copy of the shipped
list. The data gate rules a documented species the review never covered. A test
of the mechanism should not depend on how the owner answered.

## A P12 question this makes more visible

*Native Prairie Aromatics* is F189, which is open and is the owner's call: four
of its seven members are widely known as Indigenous medicines. Since this
release it passes *Edmonton natives only*, so it shows in that list and the
offline generator can pick it for an Edmonton yard. That is not new in kind,
since it was already pickable for any Alberta yard, but more surfaces now show
it. Nothing here changes it. The final reply raises it.
