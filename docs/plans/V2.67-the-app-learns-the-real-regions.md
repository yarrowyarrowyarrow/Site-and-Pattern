# V2.67 — the app learns the real regions

V2.66 built the pipeline and left the app pointed at the placeholder on purpose:
the rebuild brief scoped adoption out of the first run, because it changes which
plants get recommended for somebody's actual garden. The layer has now been
built and validated — 39 of 39 checks, then 41 of 41 — and the instruction is to
adopt it.

**Status: adopted, with eleven tests deliberately left red.** The layer is in.
Everything mechanical is done and verified against the real polygons. What
remains is one fact — the seed data still names the old regions — and it is the
author's few hours on a network, not a code change.

---

## What adoption actually is

Less than it looks, because of a decision made in V2.38 for an unrelated reason:

> "adding a region means adding a polygon and nothing else"

`src/ecoregion.py` treats **the polygon file as the vocabulary**. The filter
dropdown, the data validator's accepted keys, the site panel's detection and the
per-species range tags all read from `data/ecoregions_canada.geojson`. So the
core of a six-region-to-twenty-four-region change is: replace the file.

That is why this is tractable at all, and it is worth noticing that the
principle paid off years after it was adopted.

## Done on this branch

**The MultiPolygon bug, which would have made adoption silently wrong.**
`lookup_ecoregions` tested `type != "Polygon"` and skipped. That survived only
because the six hand-traced shapes were single rings. Every published ecoregion
layer is full of MultiPolygons — a region with an island, or a lobe the far side
of a river, is one region drawn as several pieces — and skipping them does not
raise. It answers *you are in no ecoregion at all*, which reads to a user as
"we do not cover your area yet" rather than as a bug. Four tests now pin it.

This was a real defect before adoption and would have been a silent data loss
during it. Finding it by reading the code rather than by shipping is the whole
argument for reading the consumer before replacing its input.

**`tools/ecoregions/adopt.py`** — the converter. Reads the export, writes the
app's shape: `key` (slug of the ELC name), `name`, `where` (derived from each
polygon's own centroid rather than hand-written, so twenty-four hints cannot
disagree with the geometry), `sort` (ecozone group, then name, so a 24-item
dropdown reads by system), plus `ecozone` and `ab_subregion` carried along.

Deliberately its own command rather than part of `run`, so the pipeline can
never adopt as a side effect.

**The palette bridge.** `region_fill` falls through to the ELC ecozone palette
for a key the six-region vocabulary does not know, so the website map colours
`mid_boreal_uplands` correctly the moment the file lands, with no second edit.

## The part that is not mechanical

`data/plant_ecoregions.json` holds GBIF-derived ranges for **427 species**, and
`data/plants_master.json` carries `ab_ecoregion` heuristic tags. Both are keyed
to the old six regions, and the new vocabulary shares only one key with them
(`aspen_parkland`, which survives because ELC has a region of that name).

**They must be re-derived, not translated.** Translating is the tempting
shortcut and it manufactures evidence: a species recorded in the old
`boreal_mixedwood` rectangle would fan out to all nine Boreal Plains ecoregions,
asserting nine occurrences where the data supports one region. That is the exact
failure mode P9 exists to prevent, arriving through the back door, and it is
what the V2.38 runbook already caught once when throttled GBIF requests were
being recorded as "this plant grows nowhere".

`scripts/seed_ecoregion_ranges.py` re-runs against whatever polygons are
shipped, which is precisely the tool for this. It needs a few hours and a
network. Until it finishes, species carry no derived range under the new keys
and the filter honestly returns nothing rather than a guess.

`adopt.py --dry-run` prints the size of that gap before anything is written.

## Open question worth deciding with the map in front of you

Twenty-four regions in a filter dropdown is a lot, and they are not equally
useful to a gardener. "Wabasca Lowland" versus "Mid-Boreal Lowland" is a real
distinction to an ecologist and probably not one to somebody choosing plants for
a yard near Slave Lake.

The colours already encode the answer to this: **six ecozones as hue, the
ecoregion as a lightness step.** The same grouping could carry into the filter —
choose the system, optionally narrow to the region — which keeps all
twenty-four available without making the first choice a twenty-four-way one.

Not decided. It is a UI question best answered looking at the rendered map, and
adoption does not depend on it.

## Where it landed

3200 tests, 10 failures and 13 errors. Twelve of the errors are the
pre-existing missing-PyQt6 ones in the container. **The eleven that are new all
have one cause**: `data/plant_ecoregions.json` holds GBIF-derived ranges for 427
species and `data/plants_master.json` carries `ab_ecoregion` tags, both keyed to
the old six regions, of which exactly one — `aspen_parkland` — survives.

They should keep failing until `scripts/seed_ecoregion_ranges.py` has re-run.
A red test saying "this species claims a region that does not exist" is doing
its job; making it green by translating the keys would mean fanning one
`boreal_mixedwood` record across ten Boreal Plains ecoregions, which asserts ten
occurrences where the evidence supports one.

## Three bugs found on the way, all the same shape

Adoption did not just move data; it moved data into code written when the data
was simpler, and the same wrong assumption turned up three times:

1. **`src/ecoregion.py`** tested `type != "Polygon"` and skipped. Silent: a site
   inside a real ecoregion would report being in none.
2. **`scripts/seed_ecoregion_ranges.py:polygon_bbox`** walked `coordinates` as a
   list of rings, one level too shallow. Loud, and it would have crashed the
   very re-run adoption depends on.
3. **The test guarding that function** carried the identical assumption. A guard
   written against the shape of the old data is not a guard.

## The regression adoption caused, and the fix

V2.38 made the placeholder polygons overlap "by a fraction of a degree", so a
site near a boundary reported both regions — *"the second answer is exactly the
species list that was going missing"*.

Surveyed ecoregions **tile**. That is what makes them a classification, and it
silently deleted the behaviour: every site began reporting exactly one region,
and a garden two kilometres from the parkland edge stopped hearing about the
parkland. Restored with a measured five kilometres instead of a drafting hack,
which is both honest and better — five kilometres means five kilometres at every
boundary, rather than however wide somebody drew the overlap that day.

Calgary is the demonstration: it resolves Fescue Grassland *and* reaches Aspen
Parkland, which is what anyone standing there would tell you.

## Still to do

1. `python scripts/seed_ecoregion_ranges.py` — hours, needs a network. This is
   the whole remaining gap.
2. Decide what happens to the `ab_ecoregion` heuristic tags. Four of the six old
   keys are clean renames the survey made (`mixedgrass_prairie` is Mixed
   Grassland, `moist_mixedgrass` is Moist Mixed Grassland, `fescue_foothills` is
   Fescue Grassland, `aspen_parkland` is unchanged). The other two,
   `boreal_mixedwood` and `subalpine_montane`, fan out to ten and three regions
   and cannot be migrated without inventing evidence. Renaming four and dropping
   two is defensible; doing it unasked is not, because it changes what gets
   recommended.
3. Decide whether twenty-four options belong in one filter dropdown, or whether
   it should ask for the ecozone first. See the open question above.
