# V2.80 — the inference gets a source

The outside botanical review's original complaint, answered rather than
disclosed. Second plan of the V2.80 increment; the first is
[the-range-was-never-on-the-page](V2.80-the-range-was-never-on-the-page.md).

---

## Context

The review said the site overstates what is known. V2.75–V2.79 improved the
range *maps*; this is about the sentence at the top of every species page.

`native_provinces` was the one claim in the catalogue with no source column,
while flower colour and safety both had one. **354 of 430 species published
"AB, SK"** from an inference about ecoregions continuing across the 110th
meridian — a fact the retired generator states in its own docstring:

> *"many species listed as native to AB and SK are native to only one. They are
> reading the output of this file."*

F144 (V2.78) put a mark on it, naming the heuristic rather than saying
"unverified", and left `SOURCE_FIELD` as the seam VASCAN would write into,
with a test that would **fail the day the column appeared**. This is that day.

## Getting the archive to open at all

The author downloaded VASCAN v37.17 and `--from-archive` refused it:

```
the distribution file has no taxonID column; header was
['id', 'locationID', 'locality', 'countryCode', 'occurrenceStatus', ...]
```

`distribution.txt` is a Darwin Core **extension**. An extension does not repeat
`taxonID`; it references the core row through the column `meta.xml` declares as
`<coreid>`, which is `id`. `taxon.txt` is the core and does carry `taxonID`,
which is why `read_taxa` parsed and only the second call failed.

V2.79 recorded that this reader had "never met the real one" and was verified
against a synthetic archive. **The synthetic archive wrote `taxonID` in both
files, so it agreed with the reader about the one thing neither had checked.**
The fix is a `coreID` term that tries `taxonID` then `id`; what stops it
recurring is that the tests' shared header is now the real eight-column VASCAN
header verbatim, trailing columns included, so a row cannot be read one
position off unnoticed.

## The fireweed bug

With the archive open, 173 of the 182 phantom absences resolved and
*Amelanchier alnifolia* landed in `confirm` — the canary. Nine species did not,
and three of them were *Chamaenerion angustifolium*, *Urtica dioica* and
*Mentha arvensis*. Fireweed, stinging nettle and wild mint are not plants
anybody doubts are in Alberta, so an empty answer for them is a bug here, not a
finding about the flora.

`--explain` was added to see inside the archive, which no session in this
project can open. It printed the cause immediately:

```
9 taxa in the checklist share that binomial:
  [17491] Chamaenerion angustifolium (Linnaeus) Scopoli
          rank=species status=accepted        distribution: (none)
  [29497] ... subsp. angustifolium            distribution: AB, SK, MB native
  [29484] ... subsp. angustifolium x Chamaenerion latifolium
          rank=species status=accepted        distribution: (none)
  [29498] ... subsp. circumvagum              distribution: AB, SK, MB native

rolled up from [29484] ... x Chamaenerion latifolium
result: provinces=(none)
```

`_canonical` reduces a name to its first two words, so nine taxa collapse onto
one binomial — and **two of them are accepted at rank species**, because VASCAN
files a hybrid formula at species rank. Both scored identically in `rank_key`,
so the winner was decided by **dict iteration order**, and the hybrid won. The
roll-up started from a nothotaxon with no children and found nothing, while two
AB/SK/MB-native subspecies hung off the real species, never visited.

`_is_plain_binomial` rejects hybrid formulas and infraspecific names, and
`rank_key` now ends in a total order so two runs over one archive cannot
disagree. An arbitrary winner is bad when reproducible and undiagnosable when
not.

**The first regression test passed without the fix.** The plant's name happened
to be shorter than the hybrid's, so a length tiebreak carried it and the rule
under test was doing nothing. There is now a case with a *shorter* hybrid name,
where only the rule saves it, and that one fails when the rule is removed.

## What `--apply` writes, and what it refuses to

Two changes, and only for species VASCAN actually answered.

**The 34 narrowings.** *Echinacea angustifolia* SK-only, *Yucca glauca*
AB-only, *Quercus macrocarpa* SK-only, *Sporobolus heterolepis* SK-only. This
is the review's complaint, itemised and sourced.

**414 source stamps**, `native_provinces_source = "flora"` — `src/confidence.py`'s
existing word for *read from a published flora*, rather than a new "vascan"
nobody else knows. Using the shared vocabulary is what lets
`nativity.provenance` stop calling the claim inferred without knowing where it
came from.

Three buckets are **not** applied, each for its own reason: `not_here` is a
removal, which V2.74 routes through `excluded_taxa.json` with an authority
string; `name` is a rename, which moves plant ids, `plant_fauna_master.json`
keys and a public URL; `undetermined` is this reader failing to follow a
lineage, which is not a finding about a plant. Those keep **no source field**,
so their pages keep saying the claim is inferred — which for them is still
true.

### The second column, which is the one that changes behaviour

`native_to_alberta` is a separate column and the app's actual native filter and
Habitat Value Score input. Narrowing the province string while leaving the flag
set would put two fields in one row in contradiction, with the score reading
the stale one. Seven flags were cleared: *Quercus macrocarpa*, *Solidago
canadensis*, *Aquilegia canadensis*, *Helianthus tuberosus*, *Sporobolus
heterolepis*, *Echinacea angustifolia*, *Panicum virgatum*.

**Designs using those seven will score lower.** That is the correct number, not
a regression.

Some rows carry `"1?"` — native to Alberta, editorially uncertain — which
`db/plants.py` has always read as truthy and a plain `int()` raises on. The
comparison is by boolean, so a `"1?"` VASCAN agrees with is left exactly as it
is: the question mark is a hedge somebody meant, and overwriting it with a
clean `1` because a flora happens to agree would destroy it.

## Schema v79, and the half that fails silently

Writing `native_provinces_source` into the seed JSON is **half a change**. With
no column behind it the field is dropped on load, `provenance` sees nothing,
and all 430 pages go on saying the claim is inferred. Nothing raises: the JSON
diff looks right, the report says 414 rows stamped, and the website is
unchanged. That is entry 8 in the legacy-lessons ledger — *"I edited the seed
JSON but nothing changed"* — and it is the most expensive shape of bug in this
repo.

So: the column in `schema.sql`, `_migrate_to_v79` for existing installs, the
field carried through the seed INSERT, `_SCHEMA_VERSION` **78 → 79** so a
reseed actually fires, and `tests/test_nativity_source_column.py` asserting it
end to end through a real reseed rather than against the JSON.

The apply also imports `SOURCE_KEY` **from `src.nativity`** rather than
spelling it again, because a second copy of that string is exactly the silent
no-op described above wearing different clothes.

## Two tripwires fired, and both were right

`tests/test_nativity.py` carried a countdown: *"if this starts failing, VASCAN
has landed and `provenance` should read the column"*. It failed. Inverted
rather than deleted, so the invariant it protected — that nothing writes this
field by accident — keeps a guard, and a companion test asserts the ~20
unresolved species still carry nothing.

The second was subtler. `test_every_shipped_species_with_a_claim_gets_a_note`
passed for two releases because nothing was sourced, so an unmarked claim could
only be an unmarked inference. Now 414 species are sourced and correctly carry
**no** note — a checked value is not marked, or the eye learns to skip the
mark. The invariant generalises rather than relaxes: a published claim is
either sourced or marked, and never silently neither.

## Deliberately not done

- **The 11 removals.** *Achillea millefolium* is among them and V2.79 already
  flagged it as not a simple removal: the catalogue also carries *Achillea
  borealis*, and whether North America's native yarrow races are one species is
  a live dispute. Two others are `Malus domestica` cultivars, which are
  *supposed* to be introduced — that is the catalogue and VASCAN agreeing,
  filed under a heading that reads like disagreement. The bucketing wants
  fixing before the contents are acted on.
- **The renames.** *Urtica dioica* → *U. gracilis* and *Oligoneuron rigidum* →
  *Solidago rigida* subsp. *rigida* are both real: `--explain` shows every
  `gracilis` name is a synonym pointing at a different accepted taxon. Their own
  increment.
- **The remaining 6 undetermined.** Two are the renames above; the rest want
  `--explain` run on them before anybody decides anything.

## Could not be verified here

- **The archive itself.** `data.canadensys.net` answers 403 at this
  environment's proxy. Every fix was verified against synthetic archives built
  from the real headers, names and taxon ids the author's runs printed — which
  is much better than V2.79 had, and is still not the file.
- **How the pages look** with the note gone from 414 of them.
