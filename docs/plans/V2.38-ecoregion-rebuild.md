## 1 · Ecoregions — the full rebuild

### What's actually wrong (measured)

| tag | plants | |
|---|---|---|
| `moist_mixedgrass` | 246 | the Regina–Saskatoon belt, added late for SK |
| `aspen_parkland` | **136** | the dominant region of central Alberta |
| `mixedgrass_prairie` | 125 | |
| `boreal_mixedwood` | 86 | |

Moist Mixed Grassland outnumbers Aspen Parkland ~2:1 in an Alberta-first app centred
on Edmonton. **39 native trees and shrubs carry no parkland tag**, including Saskatoon
Berry (`mixedgrass_prairie,moist_mixedgrass` only), a defining parkland shrub. The tags
were generated heuristically and never sourced.

Two layers underneath: the shipped polygons in `data/ecoregions_canada.geojson` are
**literal rectangles** (5 vertices each), and `src/ecoregion.py:89` returns only the
*first* match.

*Correction for the record:* **"Generalist" is not a plant tag** — zero plants carry it.
It is `src/db/polycultures.py:_community_habitat`'s fallback when no member has a
recognised ecoregion. It disappears on its own once the data is real; nothing to remove.

### A structural problem to fix while we're in there

The current vocabulary conflates two different things. `aspen_parkland`,
`mixedgrass_prairie`, `boreal_mixedwood`, `fescue_foothills` and `subalpine_montane`
are **geographic ecoregions**. `riparian` and `wet_meadow` are **site-scale moisture
niches** — `src/ecoregion.py`'s own docstring admits they are "per-feature rather than
per-region at the provincial scale" and keeps them "manual-only in the dropdown".

Mixing them means "which ecoregion is my site in?" and "is this spot wet?" are answered
by one control. The rebuild should split them: ecoregion becomes purely geographic
(CEC-derived, extensible), and riparian/wet-meadow become a **habitat/moisture** axis
alongside the existing `water_needs` / `moisture` fields.

### The pipeline

1. **Real polygons.** Run the existing `scripts/prepare_ecoregions.py` against the CEC
   Level III shapefile. Its step 3 already anticipates this exact move — *"expand
   `_AB_ECOREGION_CHOICES` to match the CEC vocabulary"*. CEC covers Canada, the US and
   Mexico, so adding BC later is adding polygons and nothing else.
   *Verify the CEC licence and record it in `docs/DATA_SOURCES.md`* — that document's
   standard is that "are you allowed to have that?" has a checkable answer.
2. **New vocabulary.** CEC Level III names become the canonical keys, replacing the
   hand-rolled eight. Schema bump + `data_quality` validator update + the
   `_GROUP_ECOREGION` label table in `src/db/polycultures.py`.
3. **Derive membership.** New `scripts/seed_ecoregion_ranges.py` — the tool *and* the
   provenance record, following `scripts/seed_woody_morphology.py`. Pull georeferenced
   occurrences per species (GBIF, CC0/CC BY), intersect with the polygons, apply an
   occurrence threshold, and write per-species ecoregion sets **with a source and a
   confidence** so P9 holds: a species with three records in a region is not the same
   claim as one with three hundred.
4. **Multi-region site detection.** `lookup_ecoregion` → `lookup_ecoregions` returning
   all matches; a site near a boundary belongs to both. `set_autodetected_ecoregion`
   already accepts a list.

### The display fix (same item)

`CheckableComboBox` (`src/filter_widgets.py:50`) truncates both in the popup and in the
closed line-edit. Needs a custom item delegate drawing two lines — **full ecoregion
name**, then the geographic area in brackets, smaller and dimmer — plus a sensible
closed-state summary ("3 ecoregions" rather than a clipped list).

## 3 · Three regressions and bugs

### 3a · Row count ignored — **my regression, V2.37**

`PlacementControlsWidget` emits only `patternKindChanged` (`src/placement_controls.py:106`);
Count, rows/cols, stagger, fill, drift and circle total emit **nothing**. That was
harmless when Place-on-Map was pressed *after* setup, because `current_pattern()` was
read fresh then. Auto-arm reads it at *selection* time, so setting Count to 11
afterwards leaves the map holding `auto` → 3 plants.

**Fix:** add a `patternChanged` signal, emit from every parameter control, re-arm on it
in both panels, **debounced ~150 ms** so holding a spinner arrow doesn't round-trip to
the map per tick — which should also settle the reported lag.

### 3b · Plants floating in the air — **pre-existing, one function**

`terrainHeightAt` (`html/scene3d/02-plants.js:224`) clamps the grid *indices* but not
the interpolation *fractions*:

```js
const c0 = Math.max(0, Math.min(t.cols - 2, Math.floor(col)));   // clamped
const fc = col - c0;                                              // NOT clamped
return (h00 * (1 - fc) + h01 * fc) * (1 - fr) + …                 // extrapolates
```

Outside the terrain bbox `fc`/`fr` exceed 1 and the bilinear blend becomes a linear
**extrapolation**. Measured on a trivially gentle grid (2 m of fall over 100 m):

| distance outside the grid | height returned |
|---|---|
| 10 m | 2.2 m |
| 200 m | 6.0 m |
| 1 km | 22.0 m |

So any plant beyond the fetched elevation grid climbs into the sky, which matches the
screenshot (specks near the boundary edge, terrain grid smaller than the design).

**Fix:** clamp `fc` and `fr` to `[0, 1]`, so a point outside the grid takes the nearest
**edge** height. That is both the standard behaviour and the honest one — we have no
elevation data out there, and the edge is the best available answer rather than an
invented slope (P9). One change corrects every caller: plants, flowers, wildlife
(`07-wildlife.js`), GLB structures (`05-flowers.js:448`), walk-mode ground
(`08-modes.js:99`), the bee camera (`06-fly.js:273`) and the inspect card.

Add a unit test — the JS geometry has a Python-port precedent in
`tests/test_pattern_placement.py`.

### 3c · Sun + shade as one feature

The maths is already shared — `solar.sun_position` backs the 2D map, the 3D scene and
the fork, and `solar.KEY_DATES` already feeds **both** date pickers. This is a UI
consolidation, not a rewrite.

**Where things are now:** Sun Path is Analysis → Sun Path (`src/analysis_panel.py:112`),
needs a "Place Sun Path…" press *and* a map click to anchor the arc. Shade is Site →
Features & Shade (`src/site_panel.py:1693-1885`) with its own date combo, its own
minutes slider and a 180 ms debounce, and needs no anchor.

**The merge:**
1. **One surface: Analysis → "Sun & Shade."** Move the shade *visualisation* controls
   across; leave the existing-features **import** (tree detection, OSM buildings) on the
   Site tab — that is data entry, not analysis, and conflating them is what made
   "Features & Shade" two things under one label.
2. **One date, one clock.** A single `KEY_DATES` combo and a single minutes slider
   clamped to that date's real sunrise/sunset. Dragging moves the sun marker *and*
   sweeps the building/tree shadows.
3. **Two update rates, deliberately.** The sun marker is JS-only over a cached payload
   (already built in V2.37 — `setSunPathTime`), so it follows the drag. The shade
   recompute stays debounced at 180 ms on its worker thread, because each frame re-runs
   `zoning.site_elevation_grid` plus a full grid or polygon pass
   (`src/controllers/map_events.py:1065-1120`). If that proves too slow to feel joined,
   precomputed hourly frames are the follow-on — **not** something to promise up front.
4. **Drop the anchor step** for the common case: default the arc's centre to the property
   centroid or the site pin, so the feature works on open. Keep "place it elsewhere" as
   an option rather than a prerequisite.

Headroom is fine: `analysis_panel.py` ~590 lines under its 2450 ceiling, and
`site_panel.py` *loses* lines. `html/map/06-overlays.js` has ~230 left of 1560; if it
fills, precedent says a new chunk, not a bigger ceiling.

#### What the build found that the plan did not

**A shared clock needs a guard the two separate ones never did.** With one slider
driving both features, every drag meant to move the sun arrives at the shade handler
too — and the shade handler starts a worker thread. A scrub would have conjured an
overlay nobody asked for, on a site with no boundary, complete with a "Drop a property
pin first" toast. The debounced request now carries `only_if_active` and the controller
returns before doing any work when no shade is drawn. The flag deliberately lives on
`MainWindow` (where undo/redo and project load already maintain it) rather than being
mirrored into the panel, because a second copy is a second thing to keep in step.

**The clock was never clock time, and the label said it was.** `solar.sunrise_sunset`
and `SunPosition.hour` both document themselves as *local solar time* — noon is when
the sun is highest — and the shade worker consumes the same convention. An Edmonton
summer day therefore reads 03:36–20:38 where a phone says 05:04–22:07 MDT. The *length*
is right (17h02 against a real 17h05); the ~1½-hour offset is DST plus the distance to
the time-zone meridian, which this app has never modelled. Pre-existing on both the old
shade slider and the old sun path, and out of scope to fix here — but the merged control
is labelled **"Sun time"** with a tooltip that says so, because a label that reads as
clock time is a quiet lie (P9). Modelling the real offset is a separate change: it moves
every shade rendering the app produces.

**The caster line got duplicated, on purpose.** "Casting shade: 2 buildings · 5 trees"
answers two different questions in two places — on Site → Features, *did my import
land?*; on Sun & Shade, *will the map I am about to draw be real?*. Both call one
formatter in `sun_shade.caster_summary`, differing only in where they point you.

**Line counts, measured after:** `site_panel.py` 2460 → 2240, `analysis_panel.py`
1924 → 2214, and a new Qt-free `src/sun_shade.py` at 238. `06-overlays.js` was not
touched — the V2.37 `setSunPathTime` already did everything the merge needed from JS.
