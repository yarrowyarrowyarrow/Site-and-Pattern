# V2.87 — the trees arrive

*F161 finished: the seven native trees V2.86 staged were promoted by the
author's VASCAN run and given occurrence data by their GBIF run. The
increment is mostly checking what came back, and one thing that came back
that should not have.*

## What the author ran

The V2.86 hand-over, on their machine, pushed as `trees-from-vascan` (a
non-release branch, so no installers were built from it):

1. `fetch_flora_nativity.py --from-archive dwca-vascan-v37.17.zip`
2. `ingest_flora_nativity.py`: **promote 7, hold 0**, and every other bucket
   0 (confirm 417), so VASCAN has not moved since V2.80.
3. `ingest_flora_nativity.py --apply`: seven rows promoted.
4. `seed_ecoregion_ranges.py --resume --species` for the seven, then
   `seed_species_ranges.py` and `seed_occurrence_points.py` over everything.

## What came back that should not have

Checked file by file against V2.86 before anything else:

- `plants_master.json`: exactly the seven added, no other row touched.
- `plant_ecoregions.json`: exactly the seven added (409 → 416), no other
  species changed. `--resume` did its job.
- `plant_ranges.json` and `plant_occurrence_points.json`: the seven added,
  **and six excluded species back** (*Achillea millefolium*, *Festuca ovina*,
  *Helianthus annuus*, *Solidago nemoralis*, *Solidago simplex*, *Spiraea
  douglasii*). Five merged species also changed slightly (*Hedysarum
  americanum* 1,433 → 1,394 records, *Stachys pilosa* 776 → 815).

**The six were the hand-over's fault, not the author's.** It said to rebuild
both files with no `--species`, because given `--species` each script
replaces its whole output file. That was right as far as it went. But the
point cache keeps every record ever harvested, including species the
catalogue later excluded, and both scripts derive for every species in the
cache. The published V2.86 files had been pruned; a full rebuild undid it.
Nothing displayed them (the site and the designer only ask about catalogue
species), but they shipped in data the app loads.

**The five merged species are correct as rebuilt.** `remove_taxon.py
--merge-into` unions a merged pair's raw points in the cache and keeps the
larger derived row, and its own report says both record sets "arrive on the
next re-derivation from the cache". This was that re-derivation. The small
drops are what de-duplicating the union should produce.

### Fixed

- The six removed from both files.
- Both seeders now skip every species in `data/excluded_taxa.json` and say
  which they skipped (`data_quality.excluded_scientific_names`). A fresh
  rebuild with the fixed scripts reproduces the cleaned files byte for byte.
  It skips eight: the six, plus *Agoseris parviflora* and *Oligoneuron
  rigidum*, which the cache holds but which produce no output.
- `validate_excluded_taxa` now reads the three derived files
  (`DERIVED_BY_SCIENTIFIC`). It reported all twelve occurrences before the
  fix and none after. No derived file had ever been checked.

## What the designer does with the trees

The V2.86 comparison set, V2.86 → V2.87:

| Yard (goal) | V2.86 | V2.87 |
|---|---|---|
| Edmonton (none), (pollinator), 3,600 m² lot | unchanged | unchanged |
| Calgary (none) | 119 plants / 18 species / 87 | 105 / 18 / 87 |
| Calgary (pet + kid) | 119 / 18 / 87 | 105 / 18 / 84 |
| Edmonton (pet + kid) | 119 / 17 / 86 | 111 / 18 / 87 |
| Regina (pet + kid) | 121 / 18 / 81 | 112 / **24** / 86 |
| Regina (none), (pollinator), Calgary (pollinator) | unchanged within a point | |

No design gained a plant outside its province. The change is one tree:
**Rocky Mountain Juniper, 8 m, now appears in every yard that changed**,
beside Water Birch and Pin Cherry. It passes every rule: VASCAN says native
to both provinces, it fits a 216 m² lot by crown and height, and its GBIF
records now put it near all three cities.

Two things about that, recorded rather than acted on:

- **Its records around the cities are probably planted trees.** Rocky
  Mountain Juniper is among the most planted evergreens on the prairies, and
  GBIF does not always filter cultivated records. It is Bur Oak's 115
  Edmonton records again (V2.85). Locality ranks and never filters, and the
  province rule, not locality, is what decides nativity.
- **In every changed yard it sits next to a Saskatoon.** Its own notes say
  why that is a problem: it is the alternate host of the Gymnosporangium
  rusts that spot saskatoon and hawthorn fruit. Common and Creeping Juniper,
  in the catalogue for years, carry the same rusts, so this is not new, only
  newly visible. The companion table's "enemy" pairs only push plants a
  combined spacing apart, and rust spores travel hundreds of metres, so a
  pair would not fix it. It is a design rule (a yard with saskatoons gets no
  juniper, or the design says why it has both) and it is the author's call:
  **F169**.
