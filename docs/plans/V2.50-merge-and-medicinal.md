## The branch mistake

**V2.48, V2.49 and this increment had all been committed onto the `V2.47`
branch.** The commit messages said V2.48 and V2.49; the branches did not exist.

That is not cosmetic. `CLAUDE.md` states the convention plainly ("each release
branch contains a single increment") and names the consequence: the in-app
**Check for Updates** reads the highest `V*.*` branch on the server to decide
whether an update exists. With the newest branch still called V2.47, three
increments of work were invisible to every user of that button.

The cause was the session-start hook putting the session on `V2.47` and me
never re-reading the convention when the next increment began. The hook computes
*a* correct branch at session start; it cannot know that three increments later
the branch should have moved on.

Fixed non-destructively: `V2.48` and `V2.49` created at the commits that already
carried their work, `V2.50` at this one. **`V2.47` is deliberately left where it
is** rather than rewound to its own increment. Rewinding would be a force-push
to a branch the updater points real users at, to buy tidiness, and the content
is not wrong: anyone on V2.47 simply has newer code than the name suggests.

### The other thing this exposed

A tag named `V2.47` now exists alongside the branch, created by the release
workflow. That makes `git fetch origin V2.47` and `git log origin/V2.47`
**ambiguous**, and they resolve to the tag. Reading a stale remote-tracking ref
that way is what led me to report, wrongly, that a session's work had been lost.
In this repository, fetch with an explicit refspec:

```bash
git fetch origin refs/heads/V2.47:refs/remotes/origin/V2.47
git ls-remote --heads origin        # the authority on what exists
```

## Merging the duplicate species

Three scientific names appeared twice. One pair (*Monarda fistulosa*) is a
garden-file row already excluded from the website; the other two were in
`plants_master` itself and were simply the same plant entered twice. Names
chosen by the author:

| Scientific name | Was | Now |
|---|---|---|
| *Geum triflorum* | "Old Man's Whiskers (Prairie Smoke)" + "Prairie Smoke" | **Three Flowered Avens (Prairie Smoke, Old Man's Whiskers)** |
| *Valeriana sitchensis* | "Sitka Valerian" + "Valerian" | **Sitka Valerian** |

`scripts/merge_duplicate_species.py` is the tool and the record. Three decisions
worth keeping:

- **Field by field, not winner takes all.** The two rows were authored at
  different times and each knew things the other did not. Tag columns are
  unioned: one *Geum* row carried `medicinal` and the other did not, and picking
  a winner would have lost a real fact.
- **Notes are concatenated, not chosen.** The discarded *Valerian* row carried a
  genuinely important warning, that the valerian usually sold is
  *V. officinalis*, non-native and capable of naturalising in riparian areas.
  A merge that dropped it would have destroyed the most useful sentence in the
  pair. The stale "NOTE: DUPLICATE ENTRY" sentence is stripped, since the merge
  is what makes it false.
- **`edible_parts` is free text, not a set.** It looks like a comma-delimited
  list and unioning it shredded `roots (medicinal, not culinary)` into three
  tokens reading `not culinary)`, `root (medicinal)` and `roots (medicinal`.
  The commas are inside parentheses. It is treated as prose.

The audit also found pre-existing garbage in a shipped row,
`root (tea),root (tea)?`, which the merge drops in favour of the clean value.

Catalogue 439 to 437. The colour guard moves white 73 to 72 and pink 43 to 42
and carries the reason, because a bare number change in that table is exactly
what it exists to make somebody look at.

## Publishing the medicinal tag

V2.48 withheld it, reasoning that a public, indexed "medicinal native plants"
page is the same act as publishing the traditional-use notes. **The author has
ruled otherwise**: the tag is a generic horticultural category rather than
sourced traditional knowledge.

The `WITHHELD_ROLES` mechanism stays, empty, and is **tested against a temporary
value** rather than left as dead code, because an empty tuple proves nothing
about whether the filter works and the next tag may not be so easy a call.

**The free-text `notes` column remains withheld.** That distinction is the point:
a use *category* is not the same artefact as a paragraph describing how a plant
was prepared and for what (P12).
