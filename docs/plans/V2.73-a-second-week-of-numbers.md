# V2.73 — a second week of numbers

**F134.** Add Umami web analytics to grownativeplants.ca, so page views and
visitors can be read over months rather than over the last day.

---

## The ask, and what is actually wrong

> "I'd like to add umami web analytics to the GrowNativePlants.ca website.
> Something to track which pages people are viewing and track visitors over
> time (cloudflare only shows past 24 hours)."

V2.71 shipped F133: `--analytics-token`, Cloudflare Web Analytics, opt-in, and
disclosed in the footer of every page. That was the right call for the question
*"is anybody reading this at all"* and it answers it. It does not answer the
next question, which is the one that matters for a catalogue nobody has heard
of yet: **is readership growing, and which pages are the ones people arrive
on.** Cloudflare's free Web Analytics tier holds a short window; a month-over-
month line and a per-page ranking over a season are not in it.

So this is not "replace Cloudflare". It is "add the tool that keeps history",
and the honest shape is **both can be on at once**, because the fortnight where
you are switching is exactly when you want the old numbers and the new numbers
side by side to check the new one is recording.

## What was decided, and why

**1. Umami, on the same terms Cloudflare was admitted on.**
`static_site_render` opens with a promise: *no framework, no build step, no
CDN, no external request of any kind.* V2.71 made analytics the single opt-in
exception and set the price of that exception in three parts — off by default,
no cookie and no per-visitor identifier, and disclosed in the footer of every
page it appears on. Umami pays all three: it stores no cookie, and its visitor
count is a daily-rotating hash rather than an identifier that survives to
tomorrow. If a script needed a consent banner it would not be admitted here,
whatever it measured.

**2. The analytics vocabulary moves into its own module.**
`src/site_analytics.py`, 187 lines, ceilinged on arrival at 220 (the V2.41
precedent). Two reasons, one forced and one right:

- *Forced:* `static_site_render.py` was at 721 of its 800 permitted lines.
  Growing one provider into two in place would have spent most of the
  remaining headroom on a concern that is not rendering.
- *Right:* "which analytics providers is this build carrying, what tags do
  they emit, and what does the footer therefore have to say" is one question
  with one answer, and it was previously three module-level globals and two
  functions living among the page shells. The renderer now holds one value
  and asks it things.

**3. `Analytics` is a frozen dataclass, and the validation is a constructor.**
`configure()` raises on a malformed value rather than returning a degraded
object, because the failure mode of a loose check here is unchanged from V2.71:
these values land inside quoted HTML attributes on 1,680 pages, and a build
that quietly emitted nothing would look identical to a build that worked.

**4. The website ID is checked as a UUID, and the script URL as an https URL.**
Umami's ID is a UUID in every version that has one; a stricter check than
"non-empty" costs one regex and refuses `abc" onload="` before it is published.
The script URL is validated separately because **self-hosting changes it** —
that is the whole point of `--umami-src`, and a field that must vary cannot be
a constant.

**5. `--umami-src` defaults to Umami Cloud but is a flag, not a constant.**
Three real destinations: `cloud.umami.is` (US), `eu.umami.is` (EU region), and
whatever host a self-hosted instance runs on. The third is worth supporting for
a reason that is not ideology: **`cloud.umami.is/script.js` is on the common
blocklists**, so a fraction of visitors are not counted, and serving the script
from `grownativeplants.ca` itself is the fix. Making the URL a flag now means
that migration is a one-word change to a build command later rather than a code
change.

**6. Both providers on at once is allowed, and the footer says which.**
The disclosure is generated from what is actually configured rather than
written down once. A footer that names Cloudflare on a build that carries
Umami is exactly the class of quiet falsehood this repo keeps finding in its
own prose (V2.71 deleted an About-page claim that had been false for twenty
increments). The phrase `sets no cookies` is now asserted present in *every*
configuration by a test, so the promise cannot be lost to a rewording.

## What was deliberately not done

- **No self-hosted Umami instance.** Standing up a Postgres-backed service is
  a hosting decision with a running cost, not a code change, and Umami Cloud's
  free tier answers the question as asked today. The escape hatch is built
  (`--umami-src`), so taking that step later touches no Python.
- **No custom events.** Umami can record outbound clicks, downloads and named
  events. Every one of them is a decision about what to measure, and none was
  asked for. Page views and visitors are the ask; a page-view counter that
  needs no per-page code is the thing that keeps working as the site grows
  from 1,680 pages to 3,000 without anybody remembering to instrument them.
- **Cloudflare was not removed.** It costs nothing to leave and it is the
  control that proves Umami is recording. Dropping `--analytics-token` from
  the build command turns it off with no rebuild of anything else.
- **No `data-domains` attribute.** It would stop a local `file://` preview
  and a staging copy from polluting the numbers, but the local preview does
  not run the script over http anyway, and a wrong domain in that attribute
  silently records nothing — the same failure class the token check exists to
  prevent, reintroduced by a different door.

## What was verified, and what could not be

**Verified against a real build**, not only against the fixture: the full
catalogue was rendered with both providers on, and of the **1,680 HTML pages
written, 1,680 carry the Cloudflare tag, 1,680 carry the Umami tag and 1,680
carry the disclosure.** The build's closing line read

```
  analytics: Cloudflare Web Analytics + Umami embedded, disclosed in the footer
```

which is the one place an operator finds out what kind of build they just made.
The unit tests cover the rest of the way up to the network: malformed IDs and
URLs raising, a self-hosted URL being the one published, a build with no
analytics arguments emitting nothing, and a later build being unable to inherit
an earlier build's configuration.

**Not verified:** the container has no egress and no browser, so **no beacon
was observed arriving at any dashboard.** Whether the ID is the right ID, and
whether Umami counts the visit, is the last mile and it is the author's; the
runbook in `docs/PUBLISHING_THE_SITE.md` says what to look at and how long to
wait. Note that a well-formed ID belonging to somebody else's site builds
cleanly and records nothing, which is exactly the failure the validation cannot
catch.
