# V2.72 — the release tags were pointing at the wrong commit

> *"seems like a big deal that the releases are not pointing to what they
> should... go ahead and fix them"*

Found while chasing something much smaller: a `git push -u origin V2.71` that
failed with *"src refspec V2.71 matches more than one"*.

---

## What the ambiguity actually was, and why it had never happened before

The push failed because both `refs/heads/V2.71` and `refs/tags/V2.71` existed
**locally**. Normal work never has the tag: a clone made for one increment
fetches branches, and the tag only arrives if something asks for it by name.
Something did — recovering from a mid-session container restart with
`git fetch origin V2.71`, which resolved to the *tag* and pulled it down.

Two things follow, and only the second one matters:

- **Local, and self-inflicted.** `git config remote.origin.tagOpt --no-tags`
  plus `git tag -d $(git tag)` clears it, and a bare `git fetch origin`
  otherwise drags all 102 tags back every time — measured, not assumed.
- **The tags are load-bearing and must not be deleted.** Each one anchors a
  GitHub Release, and `github_releases.parse_release_version` reads `tag_name`
  off those releases to drive the in-app updater. Deleting them would break
  updates for every packaged build. This plan records that because the first
  instinct was to delete them, and it was wrong.

## The real fault

Looking at where the tags point:

| Tags | All point at |
|---|---|
| V1.73–V2.02 | one commit |
| V2.03–V2.09 | one commit |
| V2.10–V2.20 | one commit |
| **V2.21–V2.71** | `74f2f72` — "Merge pull request #9 from V2.20" |

**Ninety-nine of 101 version tags are on the wrong commit, and zero are
right.** Fifty-one of them share a single commit that is fifty releases old.

The cause is four words that are not in either release workflow:

```yaml
tag_name: ${{ github.ref_name }}
```

`softprops/action-gh-release` creates the tag when it does not already exist,
and with no `target_commitish` GitHub anchors a new tag to the **repository's
default branch**. `main` has not moved since the V2.20 merge, so that is where
every tag since has landed.

**Nothing about the downloads was ever wrong**, which is why this survived
fifty releases without a complaint: the `.dmg` and `.exe` are uploaded assets,
not built from the tag, and the updater reads the release's `tag_name` rather
than the tag's target. What was wrong is what the tag *says* — click "V2.65"
on GitHub and you get V2.20's source.

## The fix, in two halves

**The cause**: `target_commitish: ${{ github.sha }}` in both workflows. Both,
not one — whichever workflow reaches the release first creates the tag, so a
fix in only `release-macos.yml` would hold about half the time.

**The history**: `scripts/retag_releases.py`, a one-off. For each `V<x>.<y>`
tag with a branch of the same name, it moves the tag to that branch's tip.

Why the branch tip is the right target, and not a guess:

- It is this repo's own definition of a release — CLAUDE.md, *"Each release
  branch contains a single increment of work"*.
- It is also, in practice, what was built. Both workflows trigger on **every**
  push to a `V*` branch and update the release in place, so the last push to a
  branch is what the published assets came from. Verified on V2.71, whose
  final push (`f811b252`) has a successful macOS run and a successful Windows
  run, both after the release was first published.

Dry run by default; `--apply` writes `tags-before.txt` and prints the rollback
command before it pushes anything.

## What could not be done from the session, and why

**The 99 tags are still wrong.** The workflow fix is pushed, the script is
written and its dry run verified against the live remote, but this session's
GitHub credential **cannot write tags at all** — force-moving an existing tag
and creating a brand-new one both return HTTP 403, while branch pushes on the
same remote in the same minute succeed. The agent proxy recorded no policy
denial (`recentRelayFailures` empty), so the refusal is GitHub's, not the
egress layer's. Confirmed afterwards that the remote was untouched: no probe
tag exists and `refs/tags/V2.71` still reads `74f2f72b`.

So the repair runs from the author's own machine, once:

```
python3 scripts/retag_releases.py            # prints the plan
python3 scripts/retag_releases.py --apply    # moves them
```

## Two things found on the way, neither acted on

- **`V2.0` and `V2.1` are tags with no branch.** They sit beside `V2.00` and
  `V2.10`, which do have branches, and two branch tips name the unpadded form
  in their commit subject. Almost certainly the same two releases written both
  ways early on. The script leaves them alone and says so rather than guessing.
- **The V2.47 branch tip is a commit titled "V2.49 follow-up".** Someone
  pushed later work onto an older release branch, which also rebuilt and
  republished the V2.47 release from it. It is the only genuine case of this
  in 99 (the other two flagged by the scan are the `V2.0`/`V2.00` spelling).
  The tag still belongs on the branch tip — that is what the release contains —
  but the branch's history is not what its name claims.
