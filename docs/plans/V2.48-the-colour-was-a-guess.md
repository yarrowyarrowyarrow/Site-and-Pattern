# V2.48 — The colour was a guess, and the website only asked four questions

## Context

Four reports on V2.47, from the author:

1. *"The colour needs better sourcing for data. You have blue and yellow
   columbine as red."*
2. *"This feature should be in the plant tab of the app as well."*
3. *"There is a lot of data that is not being included in a searchable way ...
   searching by ecoregion, whether it flowers, sun/water, etc (and I do mean
   etc, look up what other data can be made searchable)."*
4. *"I want the page to look a little more highend ... no em-dashes anywhere ...
   the ecoregions map displayed including showing for each plant the map of
   ecoregions in which it is found."*

The first is a correctness bug that V2.47 created the conditions for, and it is
the one worth reading the reasoning on.

---

## 1. The colour was seeded per genus, and the filter made that visible

### What I measured

All four *Aquilegia* in the catalogue carried `#d6453a`. Correct for
*A. canadensis* and *A. formosa*; wrong for *A. brevistyla* (blue) and
*A. flavescens* (yellow). That is not a one-species typo. Across the catalogue:

| Signal | Count |
|---|---|
| Genera with 3+ species sharing exactly one hex | **32** |
| Rows whose own common name names a colour the hex contradicts | **44** |
| Distinct hexes in use across 434 species | 23 |
| Rows whose `flower_data_source` said anything but `estimated` | **0** |

So the data was *uniformly* a genus-level guess, correctly labelled `estimated`
in a column nothing displayed. **V2.47 did not introduce the error; it promoted
it from a decorative tint in the 3D preview to an answer to a question.** A
wrong tint on a floret is a cosmetic issue. A wrong answer to "show me the blue
ones" is a broken feature, and the difference is entirely that somebody can now
ask.

### The fix, and why it is only a partial one

No flora could be fetched: `bloomseye.com` was blocked in the V2.47 session and
this one has the same egress policy. So the corrections rest on two signals that
travel *with the species* and that any reader can check without trusting me:

- **`epithet`** — the Latin states it: *flavescens*, *lutescens*, *aureum*,
  *flavum*, *candida*, *ochroleucus*, *rosea*. 7 species.
- **`name`** — the accepted common name states it: "Blue Columbine", "Yellow
  Beardtongue", "White Prairie Clover". 29 species.

36 species now carry a **checkable** colour. The other 359 keep `estimated` and
are now **visibly** estimated: the species page prints *not verified* beside the
colour and the About page explains what that means. That is the honest shape of
this fix. It is not "the colour data is now right"; it is "8% of it is checkable,
92% is marked as a guess, and nothing is presented as observed that was not".

### The trap that made this hand-curated rather than a regex

A colour word in a name very often describes something other than the flower.
Five cases trip a naive audit and all five were already correct:

| Species | The colour is | Left alone |
|---|---|---|
| Red Baneberry (*Actaea rubra*) | the berry | flowers are white |
| Common Snowberry (*S. albus*) | the berry | flowers are pink bells |
| Golden Sedge (*Carex aurea*) | the perigynium | a sedge has no showy flower |
| Purple Oat Grass (*S. purpurascens*) | the seed head | wind-pollinated |
| White-grained Mountain Rice Grass | the grain | a grass |

These live in `scripts/seed_flower_colour.py:KEEP` **with their reasons**, and
the validator reads that same list, so the audit and the fix cannot drift apart
and the next person does not "fix" them back.

### Two more bugs the audit turned up

- **Two graminoids were typed `groundcover`.** *Nassella viridula* and
  *Koeleria macrantha* are bunchgrasses. A mistyped graminoid escapes the
  wind-pollinated rule in `flower_colour.py` and gets handed a bloom colour it
  cannot have. Corrected in the seed data.
- **"Violet" is the genus, not the colour.** The first validator run flagged
  *Viola orbiculata* ("Round-leaved Yellow Violet") for not being purple. Every
  *Viola* in the catalogue is called a violet. The audit now skips that word for
  that genus.

### What is guarded now

`data_quality.validate_flower_colour` runs in the standard gate: a name/hex
contradiction is an **error**, and a genus of three or more sharing one
uncheckable hex is a **warning**. It reports **0 errors and 21 warnings**, and
those 21 warnings are an accurate statement of the remaining debt rather than
noise. Fixing them needs a flora and a network, not another session of this.

## 2. Colour in the plant panel

`plant_panel.py` was documented as "AT CEILING 1600" and is actually 1549, so
the combo fitted without an extraction. The vocabulary is imported from
`flower_colour.py`, never restated: the panel, the directory and the website
read one table, so they cannot come to disagree about what colour a plant is.

The test drives the **real widget** rather than the query layer, because a facet
wired to a parameter nobody reads is exactly the V2.37 dead-control bug and only
pressing the control catches it. Verified: 439 unfiltered, 54 purple, 138 purple
plus yellow, 439 on clear.

## 3. "A lot of data that is not being included in a searchable way"

Correct. The catalogue holds **68 columns** per species and V2.47's website
filtered on four. I surveyed every column for fill rate and cardinality; the
result is `src/site_facets.py`, **23 facets** in six groups.

The ones the author named, plus what the survey turned up:

| Group | Facets |
|---|---|
| Looks | flower colour, showy flower or not, flower shape, leaf shape |
| Season | blooms in, fruits in |
| Site | sun, water, **ecoregion**, hardiness zone, native province |
| Ecology | ecological role (14 tags) |
| Plant | type, mature height, life cycle, foliage, growth rate, time to maturity |
| Practical | safety, spread, where to buy, edible, photograph |

**These are not `search_plants` parameters.** The query layer already takes
thirty-odd and is shared with the desktop; twenty more would burden every
desktop query to serve a static site. The site filters client-side over an
embedded JSON index instead, so a facet costs one derivation function and a few
bytes per species. Within a facet the values are OR, across facets AND, which is
what a filter panel means and what `search_plants` does.

**One table drives three things**: the sidebar controls, the values baked into
each index row, and the landing pages generated per value. Adding a facet adds
all three.

The guard that matters: `test_every_value_in_use_has_a_label` failed on first
run for six facets (zone 9 and 10, three role tags, Manitoba, `flower_form:
none`, six leaf shapes). An unlabelled value renders a blank checkbox that
matches real plants nobody can find, which is the dead-control bug again.

### P12, again

The role vocabulary excludes **`medicinal`**. It is a generic permaculture tag
rather than sourced traditional knowledge, but a public, indexed *medicinal
native plants* landing page is the same act as publishing the traditional-use
notes that V2.47 withheld. Declared in `WITHHELD_ROLES`, tested, and stated on
the About page rather than quietly dropped. The desktop keeps the tag.

## 4. The maps, the look, and the dashes

### The maps are rectangles, and every one of them says so

`data/ecoregions_canada.geojson` is ten hand-drawn five-vertex boxes. The
runbook says so plainly: the real CEC Level III polygons are a download that has
never run in a session with open egress. So `src/ecoregion_map.py` draws them
and **carries a caption on every drawing**. A box without a caption is a claim
about a boundary; the caption keeps it a diagram (P9). Replace the geojson and
every map on the site sharpens with no code change.

Per-species maps shade by **confidence band**, so a region derived from three
occurrence records does not look like one derived from three hundred. The
projection is equirectangular with longitude scaled by cos(mean latitude),
because at prairie latitudes a plate-carrée map is visibly stretched and one
cosine is the whole correction.

### A bug the maps exposed

Drawing the range for Wild Bergamot showed "not from occurrence records" while
*Monarda fistulosa* plainly had GBIF data. `_seed_plant_ecoregions` mapped
`scientific_name -> id` with a dict comprehension, and **three scientific names
appear twice in the catalogue** (*Monarda fistulosa*, *Geum triflorum*,
*Valeriana sitchensis*: a native row and a garden/duplicate row). The later row
won and the earlier one silently lost its derived range, falling back to the
unsourced `plants.ecoregion` tag. Now maps to all matching ids: 427 species with
ranges becomes **430**.

### No em dashes

Enforced in `_esc`, which every user-visible string already passes through, so
there is one place to get it right and no way to route around it. That matters
because most of the prose on the site comes out of the *database*, where whoever
wrote a safety note cannot be asked to remember a house style set afterwards.
388 em dashes in the V2.47 output; **0 now**, guarded by a test.

En dashes inside numeric ranges are deliberately left alone: "Jun-Jul" and
"pH 5.5-7" are a different mark doing a different job, and there is a test
pinning that too.

### The look

Design tokens with a real dark theme, a serif text face with tighter measure, a
sticky header, a two-column search layout with a grouped filter sidebar, cards
with hover lift, a hatched placeholder where a plant has no photograph, and a
statistics row on the front page. Judged by reading the output, not by looking
at it: there is no display in this container.

## What this is deliberately not

- **Not a rewrite of the colour data against a flora.** That needs a network and
  a source; what it needs from the code is already here, including the column,
  the seeder, the validator and the "not verified" marker.
- **Not real ecoregion polygons.** Same reason, and the runbook already
  describes the download.
- **Not a colour palette adviser** ("your June is all yellow"). Still a good
  feature, still a design-side analysis rather than a filter.

## What I could not verify

- **How any of it looks.** No display. The HTML is verified structurally: 595
  files, 15,495 internal links, 0 dead, 0 em dashes, no unattributed image, the
  browse script can find every card it filters. Nobody has looked at the dark
  theme on a real screen.
- **The photograph copy path.** This container's image cache is cold, so all 321
  attributable photos came out as links. The build reports both counts.
- **The 36 colour corrections** are checkable against name and epithet, which is
  what "checked" claims and all it claims. They have not been held against a
  flora.
