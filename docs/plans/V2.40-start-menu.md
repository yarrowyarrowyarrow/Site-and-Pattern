# V2.40 — a start menu, not a first-run greeting

## The ask

> *"I'd like to have a start menu where the option to load a previous design or
> start a new one appears. Anything else relevant we can consider."*

Follows V2.39, which gave designs a folder and a list. The list exists; nothing
puts it in front of you at the moment you want it, which is launch.

Branch: **V2.40**.

## What is there now

`WelcomeDialog` (F44, V2.31) already offers three doors — Generate · Start from
my yard · Open the example — and `onboarding_flow.maybe_show_welcome` shows it
**once**, gated on a `QSettings` flag. It is a good dialog aimed at the wrong
moment: it is a greeting for someone who has never used the app, and a returning
user never sees it again.

Two things it cannot do, and one thing it works around:

| | |
|---|---|
| No "continue" | Nothing remembers which design you were last in |
| No "open" | The saves browser landed in V2.39 and nothing links to it |
| Crash recovery is a *second* dialog | `maybe_show_welcome` returns early when an autosave is pending, explicitly to avoid two modals stacking on launch |

## The design

Same dialog, promoted from greeting to **start menu**: shown every launch,
still suppressible, and with rows that appear only when they mean something.

```
  ⏱  Recover unsaved work            ← only if an autosave survived a crash
  ↩  Continue — “Back Yard”          ← only if the last design still exists
  📂  Open a design                   ← the V2.39 saves list
  ─────────────────────────────
  ✨  Generate a design
  🗺  Start from my yard
  🌾  Open the example
```

A first-time user sees exactly the three they see today — the top three have
nothing to offer yet. The menu **grows into what you have**, which is the right
behaviour for a screen you see every day.

### Crash recovery moves in, and this is the "anything else"

Recovery is currently a separate modal fired on `map_ready`, and the welcome
suppresses *itself* to stay out of its way. Folding it in as the top row removes
an interaction rather than adding one, and puts the most urgent thing where the
eye lands first.

**Recovery must not depend on the menu.** If the user has ticked "don't show
this again", the old standalone prompt still fires. Unsaved work is not
something to make conditional on a preference about greetings.

### Continue needs a memory

Nothing records which design you were last in. Adding
`saves.remember_last_design()` / `last_design()`, stored in the existing JSON
config (`src/settings.py`) so `saves.py` stays Qt-free, written on load and on
save. A path that no longer exists shows **no row at all** rather than a button
that fails — a dead control is worse than a missing one, which this project has
learned twice.

## Considered and rejected

- **A non-modal start panel in the map area.** More faithful to "start menu",
  and a much larger change to the window's layout. If the modal grates, that is
  the follow-on.
- **Settings/preferences on the start screen.** There is no preferences surface
  to link to, and inventing one here would be scope creep wearing a hat.
- **Tips of the day / a news panel.** Noise on a screen whose job is to get you
  out of it, and the updater already handles "what changed".
- **A "recent designs" sub-list (3–5 rows).** The saves browser already lists
  everything newest-first, one click away. Two lists of the same thing drift.

## Risks

| Risk | Guard |
|---|---|
| The menu becomes a nag | Every launch, but one checkbox turns it off forever, and Help → Welcome brings it back |
| Recovery gets lost behind a suppressed menu | The standalone prompt still fires when the menu is off; tested both ways |
| Continue opens a deleted file | The row is absent unless the path exists |
| Continue loses unsaved work | Goes through the same discard confirmation as every other load |

## Second cut — it has to open *first*

> *"I want an actual window to open (ahead of seeing the map) which will be the
> 'start menu'. I'm not seeing that."*

The first cut got the contents right and the moment wrong. `maybe_show_welcome`
fired a `QTimer` 150 ms after `MainWindow.__init__` returned, so the map painted,
*then* a modal appeared on top of it. Every row worked. It still read as a
greeting over an app you could already see, which is precisely what the ask was
about — the rows were the visible half of the change and the ordering was the
half that mattered.

### The ordering

```python
choice = onboarding_flow.choose_start_action()   # no MainWindow exists yet
window = MainWindow()
window.show()
onboarding_flow.act_on_start_choice(window, choice)
```

What makes this possible is that **the menu needs nothing from the app**: every
row is decided from disk — the saves folder, the remembered last-design path, a
surviving autosave. So it can be a window of its own (parent `None`) opened
straight after `QApplication`, and `MainWindow` is built already knowing what it
is for. A test pins `choose_start_action()` as taking no arguments, because the
day it takes `main` this ordering is over.

Three things this turned up, none of them obvious from the outside:

| | |
|---|---|
| **The theme is on the MainWindow** | `_APP_STYLE` is set on `MainWindow` and reaches every dialog by inheritance. Parentless and first, the menu landed on the platform's default *light* dialog with `#a5c8a5` text on it. It now carries `ui_style.BASE_SURFACE` itself. |
| **`quitOnLastWindowClosed`** | Closing the only visible window can connect through to `quit()`. Measured before relying on it: exec'ing a dialog before `app.exec()` and closing it does **not** quit — the main loop still runs. |
| **`map_ready` fires on every page load** | The choice is acted on there (a render into an unloaded WebEngine draws nothing), so without a disconnect a later map reload would re-open the example over the user's work. |

Closing the menu means "start me on the blank map", not "never show this again"
— only the checkbox does that. `MainWindow` no longer opens the menu at all, so
there is no path on which two appear.

## What verifying it turned up

The full suite could not reach its summary line — before *or* after this change,
confirmed by stashing it. Three separate process aborts were stacked on top of
each other, each printing in a later module than the one at fault:

1. `QApplication([])` in eight test modules left Chromium without an `argv[0]`,
   so the next `QWebEngineView` **anywhere in the run** aborted. Whichever
   module builds the QApplication first decides this for the whole process.
2. As root in a container, QtWebEngine's zygote needs
   `QTWEBENGINE_CHROMIUM_FLAGS=--no-sandbox`. Environment, not code — now in
   CLAUDE.md.
3. `test_scene3d_window` called `deleteLater()` on a `Scene3DWindow` without
   `close()`, so its `closeEvent` never stopped the photo warmer. The thread sat
   parked in its wait until the next event loop processed the deferred delete —
   which was some unrelated later test opening a dialog. `python -X faulthandler`
   is what finally named it.

(3) is a real app bug as well as a test one: `Scene3DWindow` is a **top-level**
window (`super().__init__(None)`), so `MainWindow.closeEvent`'s `stop_threads`
never saw it — `findChildren` only walks the object tree. It now closes the 3D
window first.

Two guards added, because all three cost hours precisely by not naming the
culprit: `TestTheTestSuiteCanReachItsOwnSummary` rejects `QApplication([])` and
a window `deleteLater()`d without `close()`.

And with the suite finally running to the end, a **real V2.40 regression** came
out from behind the abort: `maybe_offer_autosave_recovery` returned early
whenever the start menu was on, which skipped the *whole* method — including the
"unreadable autosave → discard it" branch. But the menu draws no Recover row for
a file it could not read, so a corrupt autosave was left with nothing to ever
clean it up. The stand-aside now wraps only the part that shows a dialog. In the
same spot: the menu asks "is there an autosave?" before the MainWindow exists,
which is where the pre-V2.39 legacy-location migration used to be triggered, so
`_autosave_pending` runs it first — otherwise the one launch that needs the
Recover row is the one that doesn't get it.

## Verification

- `python -m unittest discover -s tests -t .` green.
- Qt-free: the last-design memory round-trips, forgets a deleted file, survives
  a corrupt config.
- Widget: the row set is right for a first-time user, a returning user, and a
  post-crash launch; recovery still fires when the menu is suppressed.
- Ordering (second cut): `main.py`'s call to `choose_start_action` comes before
  `MainWindow(...)` and `act_on_start_choice` after it; `MainWindow.__init__`
  opens neither; the menu opens as a real parentless window and returns the row
  that was clicked, with **no MainWindow constructed anywhere in the test**.
